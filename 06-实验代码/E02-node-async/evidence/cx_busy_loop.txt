# 反例 2：同步 CPU 忙循环
# 单线程事件循环：同步代码执行期间，任何回调都不可能插入

A. 对照：15 个 20ms 定时器依次等待
   总耗时 465.9ms（理论 300ms）  事件循环延迟 mean=5.51ms max=6.20ms
   注：Windows 定时器粒度约 15.6ms，sleep(20) 实测约 31ms，故总耗时高于理论值；
       本节只关心延迟统计与 B/C/D 的相对差，绝对值不作断言。

B. 反例：排一个 20ms 定时器，紧接着执行 300ms 同步忙循环
   定时器实际晚到 280.4ms（期望 20ms 准时）
   => 超时判定、取消回调、心跳、日志刷新在这个窗口里全部失效

C. 反例：4 个 100ms 同步忙循环，交给 concurrency=4 的池
   并发峰值 4（上限确实是 4，池没有违约）
   总耗时 401.0ms ≈ 4 × 100ms，而不是 100ms
   => 池允许 4 个「同时开始」，但 CPU 只有一个，实际是串行执行

D. 对照：同样 4 个任务，但等待的是 100ms 定时器
   总耗时 107.8ms ≈ 100ms
   => 同样的并发上限，异步等待才真正重叠；差别不在池，在任务本身是否让出线程

判定：
- 并发上限只约束「同时在飞的任务数」，不提供 CPU 并行。
- 同步忙循环会连超时定时器一起冻住：调用方设置的 timeoutMs 在阻塞期间不会触发，
  所以「有超时」不等于「一定在超时时间点被叫醒」。
- 处理 CPU 密集任务的正确方向是 worker_threads / 子进程，不是加大 concurrency。
