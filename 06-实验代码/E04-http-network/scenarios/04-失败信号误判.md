# 反例 04：把客户端超时当成"没连上"，把 curl 的 exit 28 当成 TCP 语义

## 症状

排障时看到"连接失败"就归因为服务端挂了；或者反过来，把某个客户端报的 `ECONNREFUSED` 当成"所有客户端都应该立刻失败"的通用结论。

## 本机实测：同一端口，两种客户端，两种结果

对 `127.0.0.1:8791`（没有进程监听）：

| 客户端 | 结果 | 耗时 |
| --- | --- | --- |
| Node `net.connect` | `ECONNREFUSED` | 约 3ms |
| PowerShell `TcpClient` | `ConnectionRefused` | 立即 |
| Git Bash 的 `curl 8.17` | `exit 28`（超时） | 2011ms（`--max-time 2`） |

同一个目标端口、同一台机器，TCP 层明明回了 RST，curl 却等到超时。这说明 **curl 的退出码描述的是 curl 的观测，不是 TCP 规范的普适结论**。旧版 README 据此写下"本机未监听端口返回超时、ECONNREFUSED 无法复现"，是**用单一客户端的表现外推了传输层行为**，已在新版第 6.6 节更正。

## 失败信号分层

| 现象 | 能确定 | 不能确定 |
| --- | --- | --- |
| `ECONNREFUSED` | 目标主机可达，端口没有监听（或防火墙主动拒绝） | 服务进程是否曾经启动、是否绑定了别的地址 |
| `ETIMEDOUT` / curl exit 28 | 在期限内没有完成建连或响应 | 是 SYN 被丢、服务端没回、还是客户端自己过早放弃 |
| `ENOTFOUND` / DNS 错误码 | 名字解析阶段失败 | 目标服务是否存在（可能只是解析器不可达） |
| TLS 握手失败 | TCP 已连上，TLS 层没成 | 应用是否收到任何请求 |
| HTTP 4xx/5xx | 请求到达了应用并被判定 | 副作用是否已发生（写操作可能部分提交） |

本机的 DNS 反例：把 resolver 指向 `127.0.0.1:1`（无 DNS 服务），`resolve4('example.com')` 得到：

```text
ECONNREFUSED: queryA ECONNREFUSED example.com
```

这证明的是"解析器不可达"，**不是** NXDOMAIN，也不是 DNS 劫持。三者要分开写。

## 怎么修

1. 失败判据至少两条独立证据：客户端错误码 + 服务端日志/端口监听状态。
2. 换客户端复核：Node/PowerShell/curl 至少两个来源一致，再下传输层结论。
3. 写文档时把"本机观测"和"协议语义"分开；本机特例要标注客户端与版本。
4. 客户端超时后不要直接重放写请求：先查询/对账，或用幂等键安全重试（见 `failures.txt` 中"超时但服务端已提交"）。
