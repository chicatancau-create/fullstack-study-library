# 反例 01：每次请求都新建 TCP 连接

## 症状

服务端 `netstat` 里 `TIME_WAIT` 持续堆积；同一 API 在高频调用时，P99 比单次耗时多出 1 个 RTT；TLS 场景下每次请求都要重新握手。

## 反例代码

```js
for (let i = 0; i < 3; i += 1) {
  await new Promise((resolve, reject) => {
    const client = net.connect(port, '127.0.0.1', () => client.destroy());
    client.on('close', resolve);
    client.on('error', reject);
  });
}
```

`net.connect` 每次创建新 socket，用完即销毁。服务端会看到 3 个不同的源端口。

## 对照：连接复用

```js
const agent = new http.Agent({ keepAlive: true, maxSockets: 1 });
// 两个 http.request 共用 agent，服务端 'connection' 事件只触发 1 次
```

## 实测（本机）

`evidence/network-depth.txt`：

```text
TCP：3 次独立连接建立耗时 2.67ms/local:58271, 1.14ms/local:58272, 0.61ms/local:58273
TCP：服务端观察到 3 个入站连接，端口各异 => 每次新建连接（短连接）
TCP 复用：同一 keep-alive Agent 发 2 个请求，服务端新建连接数=1（期望 1）
```

`tests/network.test.js` 用同样的断言固化了这两条结论（`inbound.length === 3`、`connections === 1`）。

## 为什么会踩

- 在函数内部 `new http.Agent()` 或 `agent: false`，每次调用都绕过连接池。
- 用 `fetch` 默认实现时以为"客户端会自己复用"，但 Node 的 undici 也会按 origin 建池；真正打断复用通常是显式 `connection: close` 或每次新建 Agent。
- 短连接本身不是错：低频、一次性脚本、需要隔离状态的场景可以接受；错在**高频路径上无意识地放弃复用**。

## 怎么修

1. 进程级共享一个 keep-alive Agent（或全局 undici dispatcher），并设置合理的 `maxSockets`。
2. 设置 `keepAliveMsecs` 与空闲超时，避免连接被中间设备静默回收后仍被复用。
3. 服务端确认 `Connection` 头与自身超时匹配；不要让服务端 5s 关连接、客户端 60s 才复用。
