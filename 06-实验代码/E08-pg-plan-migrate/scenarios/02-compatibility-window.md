# 场景 02：兼容窗口里哪一个格子必然坏

## 触发条件

schema 有三个版本：`N-1`（只有 name）、`N`（多 email，可空）、`N+1`（再多 email_norm）。应用有 old/new 两版。

## 观察到的现象

12 个读写格子的实际结果（`src/compat.mjs`）：

| 应用 | N-1 读 | N-1 写 | N 读 | N 写 | N+1 读 | N+1 写 |
| --- | --- | --- | --- | --- | --- | --- |
| old | OK | OK | OK | OK | OK | OK |
| new | 42703 | 42703 | OK | OK | OK | OK |

新应用在 `N-1` 上读/写都失败，错误码是 `42703`，不是超时或空值——这决定了发布顺序必须是**先上 schema，再上新应用**。

## 判读

- `evidence/compat.txt` 必须打印 `matrix cells=12` 与 `new app vs schema N-1: read=42703 write=42703`。
- 若 new 在 N-1 上返回 OK，说明测试根本没查新列，矩阵是假的。

## 边界

只覆盖列增删造成的读写不兼容；未覆盖约束、默认值、函数签名、消息格式兼容。
