# 知识库目录与维护规则

> 目标：一个学习项目只保留一个总目录；现行计划、外部资料、历史快照和执行证据各归其位。新增内容先归入既有分类，不在 `E:\OBsidian` 顶层另建同项目的恢复、备份或临时目录。

## 一、当前权威入口

- 学习总入口：[[../000-学习总览|000-学习总览]]。
- 实际排期：[[../03-执行计划/深度路线与工时预算|深度路线与工时预算]]，使用 D01–D96 与 G0–G9。
- 当前进度：[[../03-执行计划/进度看板|进度看板]]，未实际验证的能力保持未评估。
- 岗位与验收：[[岗位能力矩阵与验收标准|岗位能力矩阵]]、[[综合实操考核与上岗准入|综合实操考核]]。
- 技术范围：[[技术栈全景地图|技术栈全景地图]]。

[[../03-执行计划/36周执行计划|36 周执行计划]] 与旧阶段页中的 C 周次仅作压缩主题索引，不覆盖深度路线。`90-历史归档` 中的旧总览、旧看板和旧记忆均不是现行依据。

## 二、根目录职责

| 路径 | 只放什么 | 不应放入什么 |
| --- | --- | --- |
| `000-学习总览.md` | 当前唯一学习入口与路线导航 | 历史版本全文、临时草稿 |
| `01-阶段课程/` | 阶段 00–10、原理/算法/系统/高并发等正式课程 | 项目代码、下载的整个外部仓库 |
| `02-项目实战/` | 项目需求、架构、验收、复盘及代码仓库链接 | `node_modules`、构建产物、依赖目录 |
| `03-执行计划/` | 深度路线、压缩索引、长期路线、看板和模板 | 已过期的自动生成副本 |
| `04-资源与评估/` | 技术地图、官方资源、岗位矩阵、考核、自检与维护规则 | 无来源、无许可说明的大批采集文件 |
| `05-外部资料库/` | 有来源和许可记录的第三方参考资料及索引 | 当前学习进度、正式课程正文 |
| `90-历史归档/` | 只读历史快照、迁移说明和必要的恢复信息 | 当前笔记、新的学习日志 |

根目录不新增 `recover`、`backup`、`temp`、`新建文件夹` 等平行目录。确需长期保留的历史内容进入 `90-历史归档`；AI 迁移备份进入 `.workbuddy/backups`；真正的临时材料完成验证后安全清理。

## 三、一个项目一个文件夹

1. 本目录就是“全栈工程师学习计划”的唯一总目录，外部不再保留同项目的恢复目录。
2. 每个编码项目在实际开发时使用独立文件夹或 Git 仓库；本库的项目页记录其绝对/相对链接、运行命令与证据。
3. 项目内部可按 `docs/`、`src/`、`apps/`、`tests/` 等分层，但不把多个独立项目直接散落在同一级。
4. 不把依赖、构建产物、测试数据库或密钥放入 Obsidian 学习库；配置示例使用 `.env.example` 和安全占位值。
5. 项目复制版本必须说明用途；无明确用途的副本不进入正式目录。

## 四、新增与命名规则

- 新阶段沿用 `阶段NN-主题.md`；跨阶段深入内容使用 `专项-主题.md`。
- 新项目沿用 `项目NN-主题.md`，并登记到 [[../02-项目实战/项目实战总览|项目实战总览]]。
- 新模板使用 `模板-用途.md`；新评估或导航文档放入 `04-资源与评估`。
- 文件名准确表达内容，不使用 `最终版`、`最新版2`、`副本` 等无法判断代际的名称。
- 新增文档必须补充入口链接、适用范围和验收/维护方式；没有用途的材料不正式入库。

## 五、历史归档规则

- 历史快照原样保留目录和文件名，不与现行同名文件合并，不批量覆盖现行版本。
- 快照中的 Wiki 链接反映当时目录，可能指向不存在的旧文件；归档区不参与现行文档的“零失效链接”要求。
- 不为让旧链接指向现行文件而批量改写历史正文；需要比较时同时打开当前版与指定快照。
- 回滚采用逐文件对照和人工确认，不运行来源不明的整库恢复脚本，不覆盖新增学习记录。
- 归档说明见 [[../90-历史归档/README|历史归档说明]]。

## 六、外部资料规则

- 外部资料先阅读 [[../05-外部资料库/README|外部资料库说明]] 和 [[../05-外部资料库/资料索引|资料索引]]，按主题取用，不将全部仓库当学习路线。
- 保留 `.source.json`、许可证、采集时间和哈希等来源信息；无许可或限制许可的资料仅按原说明本机学习，不擅自再发布。
- 框架 API 和版本行为回到 [[官方学习资源|官方文档]] 核对；第三方资料中的结论不能直接替代实测。
- 外部资料规模较大，可按其 README 指引在 Obsidian 排除索引，但不要因此删除来源元数据。

## 七、移动、备份与验证清单

任何目录移动或文件重命名执行以下顺序：

1. 记录源路径、目标路径、文件数量和当前修改，确认目标不存在重名覆盖。
2. 在 `.workbuddy/backups/<日期-用途>/` 创建项目内备份，并核对 SHA-256。
3. 小批移动，逐批验证文件数量、哈希和必要的目录结构；失败即停止并保留证据。
4. 更新当前入口、导航和受影响链接；历史快照正文保持原样。
5. 对 `01`–`04` 的现行 Markdown 检查 UTF-8、主标题、代码围栏、表格和 Wiki 链接。
6. 确认外部源目录已空并安全移除空目录；备份保留在项目内，不留在 Obsidian 顶层。
7. 记录迁移结果、备份位置和回滚方式；未执行的 GUI、外链或代码验证明确标注。

## 八、日常维护

- 每周只更新当前看板和学习证据，不为每周生成一份完整计划副本。
- 每月检查根目录是否出现新的恢复、临时或重复目录，并先确认归属再整理。
- 每季度复审技术地图与长期专项，旧版本进入历史归档而不是覆盖后失去痕迹。
- 新增、移动或删除正式文档后，重新检查入口和内部链接。
- 备份不是版本管理替代物；编码项目使用 Git，整个 Obsidian 库另保留独立的历史版本或备份。
