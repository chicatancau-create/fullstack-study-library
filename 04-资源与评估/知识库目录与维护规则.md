# 知识库目录与维护规则

> 目标：一个学习项目只保留一个总目录；现行计划、外部资料、历史快照和执行证据各归其位。新增内容先归入既有分类，不在 `E:\OBsidian` 顶层另建同项目的恢复、备份或临时目录。

## 三、一个项目一个文件夹

1. 本目录（`E:\OBsidian\全栈工程师学习资料库`，原「全栈工程师学习计划」）是这个学习项目的唯一总目录，外部不再保留同项目的恢复或备份目录。
2. 每个编码项目在实际开发时使用独立文件夹或 Git 仓库；本库的项目页记录其绝对/相对链接、运行命令与证据。E01–E13 的实验件统一放在 `06-实验代码/E0N-主题/`，每个实验一个子目录，`build/` 不进 Git。
3. 项目内部可按 `docs/`、`src/`、`apps/`、`tests/` 等分层，但不把多个独立项目直接散落在同一级。
4. 不把依赖、构建产物、测试数据库或密钥放入 Obsidian 学习库；配置示例使用 `.env.example` 和安全占位值。
5. 项目复制版本必须说明用途；无明确用途的副本不进入正式目录。

## 四、新增与命名规则

- 新阶段沿用 `阶段NN-主题.md`；跨阶段深入内容使用 `专项-主题.md`。
- 新项目沿用 `项目NN-主题.md`，并登记到 [[../02-项目实战/项目实战总览|项目实战总览]]。
- 新模板使用 `模板-用途.md`；新评估或导航文档放入 `04-资源与评估`。
- 文件名准确表达内容，不使用 `最终版`、`最新版2`、`副本` 等无法判断代际的名称。
- 新增文档必须补充入口链接、适用范围和验收/维护方式；没有用途的材料不正式入库。

## 五、历史归档规则

- 历史快照原样保留目录和文件名，不与现行同名文件合并，不批量覆盖现行版本。
- 快照中的 Wiki 链接反映当时目录，可能指向不存在的旧文件；归档区不参与现行文档的“零失效链接”要求。
- 不为让旧链接指向现行文件而批量改写历史正文；需要比较时同时打开当前版与指定快照。
- 回滚采用逐文件对照和人工确认，不运行来源不明的整库恢复脚本，不覆盖新增学习记录。
- 归档说明见 [[../90-历史归档/README|历史归档说明]]。

## 六、外部资料规则

- 外部资料先阅读 [[../05-外部资料库/README|外部资料库说明]] 和 [[../05-外部资料库/资料索引|资料索引]]，按主题取用，不将全部仓库当学习路线。
- 资源身份、来源、分类、许可、时效和生命周期以 [[../05-外部资料库/catalog.json|catalog.json]] 为唯一长期事实源；`材料清单.md` 与 `资料索引.md` 是生成视图，统计区禁止手工改数。
- 保留 `.source.json`、许可证、采集时间和哈希等来源信息；无许可或限制许可的资料仅按原说明本机学习，不擅自再发布。新增、更新、拒绝或归档按 [[../05-外部资料库/资料入库与扩充规范|资料入库与扩充规范]] 执行。
- 框架 API 和版本行为回到 [[官方学习资源|官方文档]] 核对；第三方资料中的结论不能直接替代实测。
- 外部资料规模较大，可按其 README 指引在 Obsidian 排除索引，但不要因此删除来源元数据。
- 调用 `05-外部资料库` 的脚本必须带 `\\?\` 长路径前缀扫盘：个别 CDN 配图名拼出的绝对路径接近 260 字符，普通 `os.walk`/`open` 看不见这类条目，会把「存在」误报成「缺失」。本机统一入口为 `python 05-外部资料库/_采集暂存/catalog_tool.py generate|validate`；`validate` 默认 `source-only`，原机严格镜像检查用 `--mode strict-mirror`，默认只读。
- 数据缺口、未核实历史处置和需要用户/导师提供的资产见 [[../05-外部资料库/资料补缺清单|资料补缺清单]]；不得为了清零指标填猜测值。

## 七、移动与验证清单

任何目录移动或文件重命名执行以下顺序：

1. 记录源路径、目标路径、文件数量和当前修改，确认目标不存在重名覆盖。
2. 移动前工作区必须干净（`git status` 无未提交改动），历史由提交本身承担，不再另建 `.workbuddy/backups` 或 Obsidian 顶层备份目录。
3. 小批移动，逐批验证文件数量和必要的目录结构；失败即 `git checkout`/`git restore` 回到上一个提交，不保留中间态。
4. 更新当前入口、导航和受影响链接；历史快照正文保持原样。
5. 对现行 Markdown 跑 `python 05-外部资料库/_采集暂存/catalog_tool.py validate --mode strict-mirror`（原机）或 `--mode source-only`（干净克隆），检查 catalog/Schema、统计、生成视图、UTF-8/BOM、一级标题、代码围栏、表格列数、Wiki/普通本地链接及镜像可提供性；归档区按第五节豁免。
6. 确认外部源目录已空并安全移除空目录。
7. 记录迁移结果与对应提交号；未执行的 GUI、外链或代码验证明确标注。

## 八、版本管理与日常维护

本库已用 Git 管理，两个远端：国外 `chicatancau-create/fullstack-study-library`（GitHub 私有）与国内 `zhoumoyukuai/fullstack-study-library`（GitCode 私有，`git remote` 名 `domestic`）。推送须由用户明确授权；GitHub 走本机 7897 代理，GitCode 直连。版本化范围是计划正文、`catalog.json`、Schema、索引与账本；`05-外部资料库/题库/`、`05-外部资料库/知识库/` 的镜像正文由 `.gitignore` 排除，重建与使用边界见 [[../05-外部资料库/材料清单|材料清单]] 与 [[../05-外部资料库/README|外部资料库说明]]；`_采集暂存/` 的采集与校验脚本连同 JSON 报告按用户 2026-11-05 指令同样**不进远端**，只留在本机，文档里的复算命令都指本机执行。轻量只读校验器是否入库，另行确认。

- 每次新增、移动、删除或修改正式文档后提交一次；推送前跑一遍校验脚本，提交信息写清改了什么、为什么。
- 回滚使用 `git log` / `git diff` / `git restore --source=<提交>`，不使用整库恢复脚本，不覆盖新增学习记录。
- 不再创建项目内备份副本；需要长期保留的历史内容进入 `90-历史归档` 并提交，需要跨机恢复时从远端克隆。
- 编码项目使用自己的 Git 仓库，本库只登记链接、运行命令与证据。
- 每周只更新当前看板和学习证据，不为每周生成一份完整计划副本。
- 每月检查根目录是否出现新的恢复、临时或重复目录，并先确认归属再整理。
- 每季度复审技术地图与长期专项，旧版本进入历史归档而不是覆盖后失去痕迹。
- 新增、移动或删除正式文档后，重新检查入口和内部链接。
- 外部资料镜像正文不进 Git，因此 `catalog.json` 必须与磁盘和来源证据同步；`材料清单.md`、`资料索引.md` 由生成器重建。未知字段保留 `null` 并进入补缺清单，不能为了“整齐”猜分支、commit 或哈希。
