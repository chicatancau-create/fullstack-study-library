# 对抗式审查：这批资料真的满足计划的用途吗

> 方法：以第一性原则拆「学习材料对本计划的功能」，再用脚本实测每一项是否被真正履行；对自己上一轮的结论逐条反驳。凡判定与实测分开标注，未量到的写「未证实」。
> 本文数据来自 `_采集暂存/AUDIT.json`、`bank2.log`、`measure2.json`（第二轮增补见文末）。

## 一、把「用途」先定义清楚

计划要的不是「读过」，而是能独立交付并通过 G0–G9 关口。因此一份材料只有六种用法有价值：

| 编号 | 功能 | 判定标准（本轮实测口径） |
| --- | --- | --- |
| F1 | 离线题面 | 文件里能读到完整题干（题目描述/示例/约束），不需要上网 |
| F2 | 可对照的解答与原理 | 题解或机制解释，用于复盘 |
| F3 | 可运行验证 | 仓库自带测试或可执行示例 |
| F4 | 路线与优先级校准 | 题单顺序、知识地图、缺口清单 |
| F5 | 图解 | 图像是内容本体，缺图即缺知识 |
| F6 | 评测口径 | 指标定义与实现，能支撑「准确率/召回/拒答率」这类要求 |

## 二、审计推翻了上一轮的三个结论

### 1. 我把最高价值的仓库评成了「中」——错

`doocs/leetcode` 在上一版索引里标注为「中：多语言对照」。实测它是**唯一承担 F1 的算法仓库**：

```text
solution README.md（中文）4,104 个   含「题目描述」 4,100 = 99.9%   含解法讲解 4,094 = 99.8%
带 difficulty/tags 前置元数据 4,033   难度分布 简单 975 / 中等 2,138 / 困难 987
英文 README 4,104 个；另含 剑指Offer(lcof 77) / lcof2 120 / 面试金典(lcci 220) / LCP 83
```

对照：`wisdompeak`（题面标记 2%）、`neetcode`（10%）、`halfrost`（88%，但那是 Go 注释里的示例）——它们的价值是 F2/F3，**不能当题面用**。上一轮我说「算法题单齐了」，严格讲只有题单齐，题面只有一家齐。

### 2. 题面与解法同页，结构上就违反计划自己的验收规则

计划第 12 行写明「不把看过题解计为完成」。而 doocs 每题把题面与解法放在同一个 README 里，随手打开就是答案。

已用无损方式解决：按原仓库自带的 `<!-- problem:start/end -->`、`<!-- solution:start/end -->` 注释切分，生成**派生视图**（原文一字未改）：

```text
题库/算法题解/_派生视图/题面/   4,100 个（只含题干+示例+约束+难度标签，附自测记录表）
题库/算法题解/_派生视图/答案/   4,100 个
题库/算法题解/_派生视图/索引.csv 可按难度/标签筛题
跳过 1 个（无 problem 区段）
```

派生文件里嵌了计划要求的每题记录项（首次是否独立、耗时、不变量、复杂度、边界、替代方案、变体、工程连接），这样「独立重做」才有落笔处。

### 3. 「公司高频题只能当题型池」这句太保守——可以做连接

把已入库的 ByteDance/TikTok CSV 与本地题面池按标题连接，实测 **408 道高频题能在本地直接拿到题面**（清单见 `题库/算法题解/_派生视图/生成说明.md`）。仍未证实的是这些标签的时效：三套 CSV 分别是 2024-06／2026-08／2026-10 的抓取，LeetCode 官方已限制公司标签访问，所以「最新高频」这句话依然不能写。

## 三、检索方法本身有偏差（第二轮已改）

第一轮我按 star 排序找仓库。第二轮扫荡 4,030 个候选后按 star 排前 60，几乎全是软件项目：`ollama`、`bootstrap`、`langchain`、`dify`、`redis`、`spring-boot`、`playwright`、`electron`……**GitHub 的热度衡量的是工具，不是学习价值**。

修正方式（已写入脚本，非口头承诺）：

1. 加 `language:markdown` 限定与文档型主题词重跑检索；
2. 下载压缩包后先按**元数据形态**粗判（md 占比、代码体积、是否教程类描述），
3. 抽取后再按**正文内容**终判：题面/问答标记数、md 篇数与字节数，不合格就删除抽取结果并记为 drop 附理由。

## 四、体积与正文错配：两处该降级

| 仓库 | 体积 | 正文 | 结论 |
| --- | ---: | ---: | --- |
| `0voice/from_coder_to_expert` | 697 MB | md 1 篇 | 文章 PDF 堆，不是知识库；只在明确要找某篇时按文件名查 |
| `cen6667/408` | 323 MB | md 3 篇 | 课程 PDF 堆，同上 |

这两处合计 1 GB，换到 4 篇正文。上一版我把它们放进「知识库/后端进阶」「知识库/计算机基础」并算进覆盖度，是**用体积冒充价值**，现更正为「按需查，不计入学习进度」。

微软四门课 5.0 GB 属另一类：notebook 内嵌输出与 webp 配图占大头（AI 课 ipynb 1.4 GB），但正文里的提问是真实 F1/F2 材料（提问标记 Web-Dev 1,529、Data-Science 3,134、AI 670）→ 保留，README 里已给出裁剪方法（在 `BULK_EXT` 加 `.ipynb` 可省约 2.5 GB）。

## 五、F3「可运行验证」远比想象窄

按测试文件数实测，真正能「跑起来验证」的只有少数几个：

```text
halfrost/LeetCode-Go            810    freeCodeCamp/freeCodeCamp   348
krahets/hello-algo              372    openai/evals                31
TheAlgorithms/Python            30     sanchit0496/reactjs-machine-coding-challenges 28
crossoverJie/JCSprout           29     doocs/leetcode              4
```

中文八股与系统设计类仓库测试文件基本为 0。**所以不能对整库宣称「可验证」**；能验证的部分只能承担 F2/F4。

## 六、正面结论（也带数据）

- **冗余极少**：跨仓库共享正文最多 8 篇，且集中在微软课程之间；81 个仓库不存在大面积互相抄。
- **完整性**：`VERIFY.json` 全量复核 81 仓库，记账无漂移、0 缺失目录、0 断链；空文件 801 个经重下上游压缩包对比，确认是**上游占位**（如 `11.1.6 MongoDB和关系型数据库术语对比图.md` 在 tar 里就是 0 字节），非抽取截断。
- **图解补上了**：外链配图 9,166 请求 → 7,099 落地；`CS-Base`、`代码随想录`、`JavaGuide`、`halfrost` 仓库内本地图片接近 0，全靠这次补取才有 F5。永久丢失的（上游 404）1,283 张已逐仓库记录。
- **路径缺陷已修**：JavaPark 4 个 PNG 因 CSDN 查询串当文件名导致路径 260 字符撞 Win32 上限，普通工具读不到；改短名后 4/4 可读，映射在 `rename_map.json`。

## 七、我这一轮流程里犯过的错（记下来防止重犯）

| 错 | 后果 | 处置 |
| --- | --- | --- |
| 把「连接提前关闭」当下载完成 | 半截压缩包记成成功 | 改整包 gzip 解压 + tar 成员扫描双校验 |
| 校验器不处理百分号编码/`?raw`/锚点 | 假报 638 处图片缺失 | 修校验器，真实数：本地可解析 34,475／缺失 2,254／外链 54,093 |
| 用 heredoc 写 `\\?\` 反斜杠被吞 | 「长路径可读」测试无效，误判 | 改用脚本文件，实测 4/4 可长路径读，随后改名修复 |
| `get()` 限流耗尽隐式返回 `None` | 检索脚本静默崩，批次空跑 | 补兜底返回；不再依赖 core 配额 |
| glob 写成 `"/**/*.md"`（绝对路径） | 越界读到 `E:\$RECYCLE.BIN` 里别的项目文稿并打印两篇 | 只读未写入；已复核库内 0 残留、无 `$` 路径；此后所有脚本一律用显式基路径 |
| 中间产物一度落到 C 盘 | 违反你的落盘要求 | 全部迁到库内 `_采集暂存`，C 盘我建的文件删净（回收 3 MB），后又删包回收 6.99 GB |
