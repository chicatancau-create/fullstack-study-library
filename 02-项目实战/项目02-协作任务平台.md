# 项目 02：协作任务平台

**对应阶段：阶段 04–05｜建议周期：4–5 周｜类型：前后端分离业务应用**

## 项目目标

实现一个多用户任务协作应用，证明认证授权、REST API、关系建模、事务、前后端契约和集成测试能力。

## 用户故事

- 用户可以注册、登录、退出并维护个人资料。
- 工作区所有者可以邀请成员、调整有限角色和移除成员。
- 成员可以在有权限的项目中创建、编辑、分配和评论任务。
- 用户可以按状态、负责人、优先级和关键词筛选任务。
- 无权限、资源不存在、请求冲突和网络失败均有明确反馈。

## MVP 范围

- [ ] 注册、登录、退出、当前用户；密码使用专用哈希算法。
- [ ] 工作区、成员、项目、任务、评论五类核心实体。
- [ ] Owner / Member 两种角色即可，服务端逐资源鉴权。
- [ ] 任务 CRUD、分配、状态流转、分页、过滤和稳定排序。
- [ ] OpenAPI、统一错误、请求 ID、输入校验和基本速率限制。
- [ ] PostgreSQL 约束、必要事务、迁移、种子数据和备份恢复说明。
- [ ] 前端加载、空、错误、成功、提交中和权限不足状态。
- [ ] 单元、API 集成、数据库和核心 E2E 测试。

## 明确不做

- 不做实时协同编辑、复杂 IM、甘特图、移动端和第三方登录。
- 邀请流程可使用受控演示方式；不接真实邮件服务也能完成 MVP。
- 不引入 Kubernetes、消息队列和 GraphQL。

## 建议实体与不变量

```text
User 1─* Membership *─1 Workspace
Workspace 1─* Project 1─* Task 1─* Comment
Task *─0..1 User (assignee)
```

- 工作区内项目名称是否唯一需明确，并由数据库约束支持。
- 任务负责人必须是同工作区成员，不能只验证用户 ID 存在。
- 评论、任务和项目必须属于同一工作区，禁止跨租户串联。
- 最后一名 Owner 不能被移除或降级，需事务与并发验证。
- 删除策略必须明确：限制、级联或软删除，不能依赖意外行为。

## API 最小集合

```text
POST   /auth/register
POST   /auth/login
POST   /auth/logout
GET    /me
GET    /workspaces
POST   /workspaces
GET    /workspaces/:id/projects
POST   /workspaces/:id/projects
GET    /projects/:id/tasks
POST   /projects/:id/tasks
PATCH  /tasks/:id
POST   /tasks/:id/comments
```

路径不是强制答案，但所有资源操作必须验证调用者与资源归属。

## 必测场景

- [ ] 未登录、其他工作区成员、非 Owner 执行管理操作。
- [ ] 非法分页、过长文本、无效状态、重复名称和跨工作区负责人。
- [ ] 并发移除最后 Owner、并发创建同名资源、事务中途失败。
- [ ] 稳定分页下新增数据的影响；空页与超范围页。
- [ ] 重复提交、请求取消、会话过期和服务端 5xx 的前端行为。
- [ ] 迁移、备份和恢复在测试环境实际执行。

## 验收标准

- [ ] 一条完整路径可演示：注册 → 建工作区 → 建项目 → 建任务 → 分配 → 评论。
- [ ] 越权测试证明不能通过修改 ID 访问其他工作区数据。
- [ ] 核心数据约束与并发测试通过，没有半完成写入。
- [ ] API 文档与行为一致，前端不依赖硬编码 mock 数据。
- [ ] CI 或本地脚本可重复执行检查，测试数据库与开发数据隔离。
- [ ] README、ER 图、架构图、认证取舍、测试证据和已知限制齐全。

## 可选扩展（MVP 验收后）

- 拖拽排序、活动日志、SSE 通知、附件、细粒度 RBAC。
- 缓存任务列表，但必须保留失效、故障与一致性说明。
