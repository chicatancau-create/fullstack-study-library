-- Go 方向：用并发限流/调度、pprof、竞态检测和高并发服务替代 JVM/Spring 专项，保留同一业务主路径。
-- Python 方向：用 GIL/asyncio、FastAPI、数据处理与 RAG/Agent 评估替代 Spring 专项。
-- C++ 方向：用 RAII、内存模型、并发、Sanitizer/Profiler 和系统项目替代企业框架中线。
-- C# 方向：用 CLR/async、ASP.NET Core、EF Core 和诊断替代 Java 企业线。
-- 替换语言不降低 SQL、权限、测试、部署、性能和故障验收；详见 [[../01-阶段课程/专项-计算机系统与多语言深度|计算机系统与多语言深度]]。
+每项新技术先写：服务哪个问题/岗位、适用和不适用场景、最小实验、版本/资料日期、与当前方案差异、测试/诊断/维护成本、升级或停止条件。没有证明新增技术的收益，就继续使用简单方案。
 
-## 四、专项选择顺序
+季度复盘只回答：交付了什么、实际验证什么、哪些假设被否定、旧系统是否仍可运行、下季度最值得补哪一个差距。重复收藏却没有编码时，停止新增资料。
 
-### A. TypeScript 全栈深化
+## 五、长期发展不由课程授予

-## 五、长期季度机制
-
-每季度只设置一个主专项，保留以下固定动作：
-
-- 70% 当前专项和项目；
-- 20% 主线/中线复习与维护；
-- 10% 新技术雷达，仅做技术卡片或最小实验；
-- 算法与系统设计进入维护节奏：每月至少一次限时套题和一次设计复盘，不靠求职前突击恢复。
-
-季度复盘回答：
-
-1. 本季度交付了什么可运行成果，验证证据是什么？
-2. 哪些技术从 P3 升为 P2，或从 P2 升为 P1？依据是什么？
-3. 哪些技术不再值得投入？停止是否影响已有项目维护？
-4. 目标岗位或项目下一阶段真正需要的能力是什么？
-5. 是否连续收藏而没有编码？若是，下季度停止新增资料。
-
-## 六、技术卡片最低字段
-
-每个中线或专项技术至少记录：
-
-- 名称、版本/文档日期、学习目标；
-- 解决的问题与不适用场景；
-- 核心概念和最小可运行示例；
-- 与主线/中线替代方案的差异；
-- 测试、性能、安全、部署和运维成本；
-- 学习产出与证据链接；
-- 继续深入、保持认知或停止投入的结论。
-
-## 七、长期完成标准
-
-不是把全景地图全部勾选，而是达到：
-
-- 主线和中线各能独立交付，底层概念可以跨栈迁移。
-- 至少两个 P2 专项有真实作品或问题验证。
-- 面对陌生框架能读官方文档、做最小实验、建立测试并评估成本。
-- 能维护旧项目、升级依赖、处理安全问题和迁移，不只会创建新项目。
-- 技术选择有约束、证据、替代方案和退出策略。
+持续关注目标岗位官方 JD 的变化，每季度更新一次 [[../04-资源与评估/岗位能力矩阵与验收标准|差距矩阵]]，避免多年围绕已经无关的技术扩展。
