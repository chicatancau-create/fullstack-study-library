# ADR 002：支付回调以 event_id 去重 + 订单状态机收敛

## 状态

已采纳（2026-11-07）

## 背景

支付回调可能重复、乱序，也可能在用户取消订单之后到达。候选方案：

1. 只根据订单状态判断：`created` 收到 success 就置 `paid`，其他忽略；
2. 以回调 `event_id` 建唯一表，事务内先锁订单再插入事件，按状态机决定是否应用；
3. 引入消息队列 + 消费位点。

## 决策

采用方案 2：`p03.payment_events.event_id` 主键唯一；回调事务先 `SELECT ... FOR UPDATE`
锁订单，再 `INSERT ... ON CONFLICT DO NOTHING` 记录事件；`success` 且订单为 `created`
才置 `paid`，订单已取消则返回 202 并记录 `applied=false`。

## 原因

- 方案 1 无法区分“同一事件重放”和“新事件”，审计缺失，重复回调会重复写业务副作用（本 Demo 的副作用只有状态）。
- 方案 3 超出项目范围，且仍需要事件去重表。
- 方案 2 把“事件唯一性”和“订单状态机”放在同一事务，天然处理取消/支付的竞争：行锁决定先后，
  后到者看到最新状态。

## 代价

- `payment_events` 持续增长，需要按时间分区或归档。
- 回调处理持有订单行锁；支付网关超时重试会放大锁等待，需要限制回调并发。
- 只解决了“至少一次投递”的重复；跨系统的 exactly-once 仍需对账任务。

## 回滚

若改为队列消费，保留 `payment_events` 作为幂等表；订单状态机与 API 契约不变。
