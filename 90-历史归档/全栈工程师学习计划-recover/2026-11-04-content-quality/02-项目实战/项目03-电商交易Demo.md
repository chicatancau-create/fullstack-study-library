# 项目 03：电商交易 Demo

**对应阶段：阶段 06–07｜建议周期：4–5 周｜类型：高正确性交易练习**

> 安全边界：本项目只实现模拟支付或明确标记的支付状态，不接真实资金、不保存银行卡数据、不用于生产交易。

## 项目目标

围绕商品、购物车、订单和库存建立正确性闭环，重点证明事务、并发、幂等、安全、性能、测试和部署能力，而非页面数量。

## 用户故事

- 访客可以浏览和搜索商品，登录用户可以加购并提交订单。
- 用户重复点击提交或重试请求，不会生成非预期重复订单。
- 库存不足、价格变化和订单状态冲突会得到明确结果。
- 管理员可以通过受控接口维护商品与查看订单，普通用户无法越权。
- 系统故障可定位、可恢复，核心指标和错误有证据。

## MVP 范围

- [ ] 商品列表/详情、购物车、订单列表/详情和受控管理接口。
- [ ] 服务端保存商品价格和库存；绝不信任客户端提交价格。
- [ ] 下单事务、库存扣减、订单快照和明确状态机。
- [ ] 幂等键、唯一约束、重复请求安全处理和并发测试。
- [ ] 模拟支付成功/失败回调，验证来源与重复回调处理；不使用真实秘密。
- [ ] 输入校验、认证授权、XSS/注入防御、速率限制和安全 Header。
- [ ] 单元、集成、并发、E2E 和基础负载测试。
- [ ] Docker、CI、HTTPS 部署、日志、指标、备份恢复和回滚演练。

## 明确不做

- 不接真实支付、物流、发票、推荐系统和复杂促销。
- 不做多商家、跨境、多币种和秒杀大促。
- 不以“高并发”名义跳过基本正确性或引入未验证组件。

## 建议模型与状态机

```text
Product 1─* OrderItem *─1 Order
User 1─* Order
Order 1─* PaymentAttempt（模拟）
Order 1─* InventoryEvent（可选审计）
```

订单状态示例：

```text
PENDING_PAYMENT → PAID → FULFILLED
PENDING_PAYMENT → CANCELLED
PENDING_PAYMENT → PAYMENT_FAILED → PENDING_PAYMENT（仅允许受控重试）
```

状态集合与迁移可按设计调整，但必须明确：

- 哪些迁移合法，谁可以触发，是否允许重复触发。
- 取消/失败是否以及何时释放库存，并发下如何保证一致。
- 商品改价不能修改历史订单快照。
- 库存不能为负，支付金额必须来自服务端可信计算。

## 核心实验

1. **重复提交**：同一用户、同一幂等键并发发送多次请求，验证业务结果。
2. **库存竞争**：库存为 5，并发请求总量大于 5，验证成功、失败和最终库存。
3. **事务回滚**：订单写入后注入失败，验证不存在孤立记录或错误扣减。
4. **重复回调**：同一模拟支付结果发送多次，验证状态不倒退、不重复副作用。
5. **故障降级**：缓存不可用、数据库慢查询、下游超时，观察超时与错误反馈。
6. **性能基线**：记录数据量、并发、P50/P95/P99、吞吐和错误率，再做单变量优化。

## 必测场景

- [ ] 空购物车、下架商品、库存为 0、数量边界和非法金额。
- [ ] 修改其他用户订单、伪造管理员、篡改价格和回调内容。
- [ ] 重复下单、并发下单、非法状态跳转和重复模拟回调。
- [ ] 长事务、锁冲突或死锁的识别与受控重试。
- [ ] 服务重启后的数据一致性、备份恢复和旧版本兼容性。
- [ ] 日志包含请求 ID 但不包含认证信息或敏感个人数据。

## 验收标准

- [ ] 核心交易不变量有自动化测试，并在并发条件下保持。
- [ ] 所有价格、权限、状态与库存判断均由服务端执行。
- [ ] 性能报告有真实测量，优化结论不只依赖主观感受。
- [ ] CI 实际通过，部署版本、迁移和回滚路径可追溯。
- [ ] 能根据请求 ID、日志和指标定位一个注入故障。
- [ ] 项目清楚标注 Demo 边界，不宣称满足生产支付合规要求。

## 可选扩展（MVP 验收后）

- Outbox + 模拟消息队列、缓存商品读模型、后台过期订单任务。
- OpenTelemetry Trace、压测环境隔离、灰度发布设计说明。
