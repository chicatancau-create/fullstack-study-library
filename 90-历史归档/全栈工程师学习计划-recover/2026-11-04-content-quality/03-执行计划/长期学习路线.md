# 长期学习路线（24 个月起步，持续迭代）

> 本路线是“36 周主线 + 16 周中线 + 长期专项”的总执行图。全部技术进入地图，但不同时学习；每个阶段仍有唯一重点和可验收交付。

## 一、总体结构：1 + 1 + N

- **1 条主线（P0）**：TypeScript/React/Node.js/PostgreSQL，先获得完整独立交付能力。
- **1 条中线（P1）**：Java/Spring Boot/Vue/MySQL，获得第二套企业交付能力并理解跨栈迁移。
- **N 个专项（P2/P3）**：Python、Go、.NET、云原生、分布式、跨端、数据、AI、可视化等，根据岗位和项目逐个选择。

技术名称全集见 [[../04-资源与评估/技术栈全景地图|技术栈全景地图]]，中线课程见 [[../01-阶段课程/阶段09-中线技术栈与多语言交付|阶段 09]]，专项课程见 [[../01-阶段课程/阶段10-长期扩展与专项深化|阶段 10]]。

## 二、24 个月推荐节奏

| 时间 | 层级 | 重点 | 必须交付 |
| --- | --- | --- | --- |
| 第 1–9 个月 | P0 主线 | 完成 [[36周执行计划|36 周执行计划]] | 四个项目、测试部署证据、作品集 |
| 第 10–12 个月 | P1 中线 | Java/JVM、Spring Boot、Vue、MySQL、Java 测试 | 同一业务跨栈实现与对比报告 |
| 第 13–15 个月 | P1 工程深化 | JVM/Node 诊断、MySQL/PostgreSQL、消息、缓存、分布式基础、K8s 入门 | 一个可靠性或性能专项、一次故障演练 |
| 第 16–18 个月 | P2 第二语言/框架 | Python 或 Go 二选一；Next.js/Nuxt/NestJS 按方向选学 | 一个非教程服务或全栈应用 |
| 第 19–21 个月 | P2 专项一 | 前端、后端、云原生、数据/AI、跨端中选一个 | 专项作品、量化结果和技术报告 |
| 第 22–24 个月 | P2 专项二/岗位补强 | 另一个专项，或针对目标岗位补齐高频要求 | 真实问题、开源贡献或综合项目迭代 |
| 24 个月后 | 持续 | 每季度一个主题，每月一次维护，每周持续编码 | 可复用知识、作品与公开技术表达 |

时间不足时按月顺延；有明确 Java 岗位目标时，可在主线阶段 05 后提前启动 Java，但不能跳过 SQL、测试、安全和部署。

## 四、专项选择顺序

### A. TypeScript 全栈深化

- **内容**：NestJS、Next.js、Nuxt、tRPC、GraphQL、Drizzle、Monorepo、BFF。
- **入口**：主线项目 04 验收。
- **产出**：同一页面在 SPA/SSR/SSG 下的缓存、SEO、性能和部署对比；或 NestJS 模块化后端。

### B. Java 企业后端深化

- **内容**：JVM、并发、Spring Security、JPA/MyBatis、MySQL、RocketMQ/Kafka/RabbitMQ、Spring Cloud 生态。
- **入口**：阶段 09。
- **产出**：一个带消息可靠性、幂等消费者、追踪与压测的模块；先模块化单体，再评估微服务。

### C. Python 后端、数据与 AI

- **内容**：FastAPI/Django、SQLAlchemy、Pydantic、Celery、pytest、Pandas、LLM/RAG/Agent。
- **入口**：任一主线后端项目完成。
- **产出**：具有权限、后台任务和测试的 API；或带评估集、引用和成本记录的 RAG 应用。

### D. Go 与云原生后端

- **内容**：Go 并发、HTTP、gRPC、sqlc/GORM、K8s、Prometheus、pprof。
- **入口**：网络、SQL、Docker 基础完成。
- **产出**：可压测、可观测、可容器部署的小服务，说明 Go 与 Node/Java 的取舍。

### E. 前端架构与体验

- **内容**：Next/Nuxt、设计系统、微前端、Monorepo、Web 性能、可访问性、可视化、PWA/WASM。
- **入口**：主线 React 项目和浏览器基础完成。
- **产出**：设计系统或复杂可视化，具备用户行为测试、性能报告和架构决策。

### F. 移动、桌面与实时媒体

- **内容**：React Native/Expo、Flutter、Electron/Tauri、WebRTC、实时协作、FFmpeg。
- **入口**：前端状态、网络、安全和部署完成。
- **产出**：一个跨端应用或实时功能，覆盖权限、断线、升级、签名或媒体成本。

### G. 数据平台与搜索

- **内容**：MongoDB、Elasticsearch/OpenSearch、ClickHouse、CDC、ETL、消息流、向量数据库。
- **入口**：PostgreSQL/MySQL、事务、索引、消息语义掌握。
- **产出**：按真实查询需求比较关系模型与专用存储，提供数据同步和一致性验证。

### H. DevOps、SRE 与安全

- **内容**：Kubernetes、Terraform/OpenTofu、Argo CD、Service Mesh、OpenTelemetry、SLO、供应链和混沌工程。
- **入口**：项目已容器化、部署、监控和恢复演练。
- **产出**：可重复环境、可追溯发布、可行动告警和故障演练报告。

## 五、长期季度机制

每季度只设置一个主专项，保留以下固定动作：

- 70% 当前专项和项目；
- 20% 主线/中线复习与维护；
- 10% 新技术雷达，仅做技术卡片或最小实验。

季度复盘回答：

1. 本季度交付了什么可运行成果，验证证据是什么？
2. 哪些技术从 P3 升为 P2，或从 P2 升为 P1？依据是什么？
3. 哪些技术不再值得投入？停止是否影响已有项目维护？
4. 目标岗位或项目下一阶段真正需要的能力是什么？
5. 是否连续收藏而没有编码？若是，下季度停止新增资料。

## 六、技术卡片最低字段

每个中线或专项技术至少记录：

- 名称、版本/文档日期、学习目标；
- 解决的问题与不适用场景；
- 核心概念和最小可运行示例；
- 与主线/中线替代方案的差异；
- 测试、性能、安全、部署和运维成本；
- 学习产出与证据链接；
- 继续深入、保持认知或停止投入的结论。

## 七、长期完成标准

不是把全景地图全部勾选，而是达到：

- 主线和中线各能独立交付，底层概念可以跨栈迁移。
- 至少两个 P2 专项有真实作品或问题验证。
- 面对陌生框架能读官方文档、做最小实验、建立测试并评估成本。
- 能维护旧项目、升级依赖、处理安全问题和迁移，不只会创建新项目。
- 技术选择有约束、证据、替代方案和退出策略。
