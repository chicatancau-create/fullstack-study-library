# 全栈工程师学习计划

> 目标：从零基础或基础不系统的状态出发，最终能够独立交付可测试、可部署、可观测、可维护的全栈应用，并具备跨技术栈迁移和长期专项深化能力。
>
> 总体节奏：**36 周主线 + 16 周中线 + 长期专项**，默认每周 12–15 小时。完整包含主要、次要和扩展技术，但不同时学习；时间不足时顺延，不通过跳过测试、项目和复盘赶进度。

## 一、先明确“全栈”的边界

全栈不是“所有框架同时都会”，而是能够完整走通以下交付链路，并能将底层知识迁移到不同语言和生态：

**需求分析 → 数据建模 → 前端交互 → 后端 API → 持久化 → 权限与安全 → 自动化测试 → 构建部署 → 日志监控 → 故障定位 → 迭代维护**

学习优先级：

- **P0 主线**：第一套必须精通的独立交付栈，以及所有跨栈底层能力。
- **P1 中线**：第二套可独立交付的企业技术栈和常见工程深化能力。
- **P2 专项扩展**：按岗位或项目选择的方向，至少用一个作品或真实问题验证。
- **P3 前沿认知**：知道解决的问题、边界和替代方案，做技术卡片或最小实验，不标记为“精通”。

完整技术生态见 [[04-资源与评估/技术栈全景地图|技术栈全景地图]]，长期顺序见 [[03-执行计划/长期学习路线|长期学习路线]]。

## 二、主线与中线技术栈

### P0 主线：TypeScript 全栈

| 层次 | 主线选择 | 选择理由 |
| --- | --- | --- |
| 语言 | JavaScript → TypeScript、SQL、Shell | 前后端统一语言，建立类型和自动化能力 |
| 前端 | HTML、CSS、React、Vite | 先掌握浏览器与组件化，不急于依赖全栈框架 |
| 后端 | Node.js、Fastify、REST、OpenAPI | 轻量、明确，便于理解 HTTP 与服务端边界 |
| 数据 | PostgreSQL、SQL、Prisma、Redis | 同时掌握 SQL 原理、ORM 和缓存，不只调用 API |
| 质量 | Vitest、Testing Library、Playwright | 覆盖单元、组件、接口和关键端到端流程 |
| 工程 | Git、npm、Linux、Docker、GitHub Actions | 建立可复现开发、持续集成和交付能力 |
| 部署 | 一个可信云平台 + 反向代理 + HTTPS | 先掌握单机和模块化单体，再考虑分布式 |

### P1 中线：Java 企业全栈

| 层次 | 中线选择 | 对照与迁移目标 |
| --- | --- | --- |
| 语言与运行时 | Java、JVM、Maven/Gradle | 集合、泛型、并发、JVM 诊断和依赖治理 |
| 前端 | Vue 3、Vue Router、Pinia、Vitest | 将 React 的组件、状态和测试经验迁移到 Vue |
| 后端 | Spring Boot、Spring MVC、Spring Security | 掌握 DI、企业分层、权限、校验和生产化能力 |
| 数据 | MySQL、JPA/Hibernate、MyBatis、Flyway/Liquibase | 比较两种 ORM/SQL 路径及 PostgreSQL/MySQL 差异 |
| 质量与运行 | JUnit 5、AssertJ、Mockito、Testcontainers、Actuator | 建立真实数据库测试、健康检查和 JVM 诊断能力 |

### P2/P3 长期技术范围

已纳入 [[04-资源与评估/技术栈全景地图|全景地图]]：

- **语言/后端**：Python/FastAPI/Django、Go/gRPC、C#/ASP.NET Core、PHP/Laravel、Rust，以及 NestJS、Next.js、Nuxt。
- **前端/跨端**：Angular、Svelte、设计系统、微前端、PWA/WASM、可视化、React Native/Flutter、Electron/Tauri、WebRTC。
- **数据/分布式**：MongoDB、Elasticsearch、ClickHouse、消息队列、CDC、微服务、事件驱动、分布式一致性与向量数据库。
- **工程/运维**：Kubernetes、IaC、GitOps、Service Mesh、OpenTelemetry、Prometheus/Grafana、SLO、安全供应链。
- **新兴方向**：LLM、RAG、Agent/MCP、数据工程、机器学习、实时协作和音视频。

约束：

1. 版本以学习时的官方 Active LTS 或稳定版为准，项目内固定版本并保留锁文件或等价依赖锁定。
2. 单个项目不混用包管理器；同类框架一次只主学一个，对比实验除外。
3. Next.js、NestJS、GraphQL、Kubernetes 等进入对应中线或专项，不与 36 周主线并行堆叠。
4. AI 可以辅助解释、生成测试和审查代码，但必须能独立说明实现、验证结果与失败原因。

## 五、每周学习与复盘机制

每周 12–15 小时建议分配：

- 20% 理论与官方文档；
- 45% 编码和项目实现；
- 20% 测试、调试与重构；
- 15% 写作、复盘与面试表达。

执行规则：

- 每 45–90 分钟形成一个可验证的小结果，而不是连续观看数小时课程。
- 每个知识点至少完成一次“不看教程重写”和一次“向他人解释”。
- 错题、Bug 和模糊概念按 **1 天、7 天、30 天**复习。
- 遇到阻塞先记录最小复现、错误原文、已验证假设；再搜索或求助。
- 每周只允许 1–2 个主要目标，新增主题进入候选清单，不打断当前闭环。
- 连续两周完成度低于 60% 时减少范围，不压缩睡眠，不跳过复盘。

## 六、完成定义（Definition of Done）

一个阶段只有同时满足以下条件才算完成：

- [ ] 核心知识能够脱离教程解释，并知道适用边界。
- [ ] 交付物可从干净环境按 README 安装、启动和测试。
- [ ] 正常路径、失败路径和关键边界均有验证证据。
- [ ] 没有明文秘密、调试残留、无效依赖和明知未处理的高风险问题。
- [ ] 能展示需求、架构、关键决策、测试、部署和复盘。
- [ ] 已更新进度看板，未完成事项明确转入下一周。

最终岗位能力自评见 [[04-资源与评估/能力自检清单|能力自检清单]]，求职材料见 [[04-资源与评估/面试与作品集|面试与作品集]]。

## 七、建议的启动方式

1. 今天只阅读阶段 00、建立进度看板，不提前安装全部技术栈。
2. 为每周预留固定学习时段，并在看板中记录实际可用时间。
3. 项目代码另建独立 Git 仓库；本知识库保存计划、笔记、复盘和项目链接。
4. 定期备份整个 Obsidian 库并保留历史版本，避免同步目录成为唯一副本。
