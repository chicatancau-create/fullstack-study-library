# 阶段 07：部署运维与系统设计

**建议周次：第 29–32 周｜优先级：P0/P1｜目标：让应用可复现交付、可观察、可恢复，并能解释架构取舍。**

## 阶段目标

- 将项目 03 部署为具有 HTTPS、数据库、备份、日志和 CI/CD 的可运行系统。
- 掌握常见故障的诊断路径，能从约束出发设计简单架构。
- 默认模块化单体；只有证据表明需要时才引入分布式复杂度。

## 学习清单

### Linux、网络与容器

- [ ] Linux 用户权限、文件权限、进程、信号、端口、磁盘和系统日志。
- [ ] SSH 基础与密钥保护；不使用共享 root 密码作为长期方案。
- [ ] DNS、反向代理、TLS、HTTPS、WebSocket 代理和超时配置。
- [ ] Docker 镜像、容器、分层、网络、卷、健康检查和资源限制。
- [ ] 多阶段构建、非 root 运行、固定基础镜像版本和减少镜像秘密。
- [ ] Compose 编排本地依赖；理解容器不是安全边界或数据备份。

### CI/CD 与发布

- [ ] CI：安装、格式检查、Lint、类型、测试、构建和必要安全扫描。
- [ ] 缓存依赖但不牺牲可复现性；失败必须阻断不合格发布。
- [ ] 环境配置、秘密管理、构建产物和不可变发布版本。
- [ ] 迁移与代码兼容性、灰度/滚动概念、回滚和数据库回滚区别。
- [ ] 备份恢复、回滚演练和故障记录；回滚不是单纯重新部署旧镜像。
- [ ] 健康检查区分存活与就绪，避免依赖故障被检查掩盖。

### 可观测性与故障响应

- [ ] 结构化日志、请求 ID、用户隐私、级别和采样。
- [ ] 指标：流量、错误、延迟、饱和度；业务与基础设施指标并重。
- [ ] Trace 的基本概念，理解跨服务因果链。
- [ ] 告警应对应可行动症状，避免只告警原因或大量噪音。
- [ ] 故障流程：发现 → 止损 → 定位 → 恢复 → 验证 → 复盘。
- [ ] 复盘关注事实、时间线和系统改进，不寻找替罪者。

### 系统设计与进阶主题

- [ ] 从用户量、数据量、读写比、延迟、一致性、可用性和成本定义需求。
- [ ] 容量估算、无状态服务、负载均衡、连接池和水平扩展。
- [ ] 缓存、队列、后台任务、定时任务和至少一次投递。
- [ ] 幂等消费者、重复消息、顺序、重试、死信和最终一致性。
- [ ] 单对象/单库事务与跨服务一致性的差异；Saga/Outbox 了解即可。
- [ ] 单体、模块化单体、微服务的组织与运维成本。
- [ ] WebSocket、SSE、GraphQL、Kubernetes 作为 P2，不在主线同时深入。

## 最小实践

1. 编写项目 03 的生产 Dockerfile 和本地 Compose。
2. 建立 CI，真实运行格式、Lint、类型、测试和构建。
3. 部署应用、PostgreSQL 与反向代理，启用 HTTPS 和必要安全 Header。
4. 增加健康检查、请求 ID、结构化日志和核心指标。
5. 演练一次旧版本回滚、数据库备份恢复和依赖不可用故障。
6. 写一页架构说明：上下文、容器、数据流、关键决策、容量和风险。

## 阶段验收

- [ ] 新环境仅依据文档和受控配置即可部署，秘密不进入镜像或仓库。
- [ ] CI 实际通过，失败场景能阻断流程；发布版本可追溯。
- [ ] 回滚与恢复演练有记录，数据库变更不会被简单旧镜像回滚破坏。
- [ ] 能通过请求 ID 串联一个错误，并依据指标判断影响范围。
- [ ] 能对一个系统设计题先澄清需求、做估算，再提出简单方案和演进路径。
- [ ] 未引入无法解释收益和运维成本的分布式组件。

## 常见误区

- 在本机能运行就视为可部署；配置、权限、时区和资源限制未验证。
- 把日志当监控，把进程存活当业务健康。
- 面试导向地堆微服务、Kafka 和 Kubernetes，却没有容量与故障依据。
