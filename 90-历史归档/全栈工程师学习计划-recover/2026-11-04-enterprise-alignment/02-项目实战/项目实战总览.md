## 跨栈与专项实践规则

- 中线不要求把四个主线项目全部重写；复用需求、API、权限矩阵和测试用例，减少重复产品工作。
- 跨栈验收必须包含对比：类型、依赖、数据访问、事务、测试、诊断、部署和维护成本。
- P2 专项至少完成一个可运行作品或真实问题验证；P3 认知项可以只做技术卡片和最小实验。
- 不为“技术收集”在同一个项目中堆叠多个同类框架、数据库或消息系统。
- 技术范围见 [[../04-资源与评估/技术栈全景地图|技术栈全景地图]]，时间顺序见 [[../03-执行计划/长期学习路线|长期学习路线]]。

## 每个项目的标准目录建议

```text
project-name/
├─ docs/                 # 需求、架构、决策、运行手册
├─ src/                  # 或 apps/、packages/，按真实复杂度选择
├─ tests/                # 不与源码混放的测试可按项目约定调整
├─ .env.example          # 仅变量名和安全示例，不含真实秘密
├─ .gitignore
├─ README.md
└─ package.json          # 以实际项目结构为准
```

小项目优先单仓、单应用；不要为了“看起来高级”提前拆微服务或 monorepo。

## 统一完成定义

### 需求与范围

- [ ] 写明目标用户、核心用户故事、MVP 和非目标。
- [ ] 将业务规则写成可验证语句，明确权限与数据不变量。
- [ ] 所有扩展项不阻塞 MVP 闭环。

### 工程质量

- [ ] 从干净环境可按文档安装、启动、测试、构建。
- [ ] 配置有示例，真实秘密未进入 Git、镜像、日志或前端产物。
- [ ] 格式、Lint、类型和相关测试有明确命令并实际执行。
- [ ] 正常、失败、空值、边界、重复请求和权限场景按风险覆盖。
- [ ] 错误不会被静默吞掉，日志不泄露敏感数据。
- [ ] 涉及用户数据时建立字段清单，写明用途、可见角色、保留和删除方式；只使用合成测试数据。

### 交付证据

- [ ] README 含项目价值、截图/演示、技术栈、架构和运行命令。
- [ ] 至少一份架构图；涉及数据库时提供 ER 图。
- [ ] 至少两份 ADR（架构决策记录）：选项、原因、代价、回滚。
- [ ] 至少一份真实 Bug 复盘，包含失败证据与回归测试。
- [ ] 至少一次有范围和结论的评审记录，发现的问题已修复或明确延期。
- [ ] 记录未验证场景、已知限制和下一步，不夸大完成度。
- [ ] 使用 [[../03-执行计划/模板-项目复盘|项目复盘模板]] 完成复盘。

## 代码审查清单

提交前逐项检查：

- 本次改动是否只覆盖需求范围，是否引入无关重构或依赖？
- 是否信任了客户端传入的用户、角色、价格、权限或资源归属？
- 多步写入是否有事务、唯一约束和幂等保护？
- 异步操作是否处理超时、取消、失败、重复和竞态？
- 测试能否在正确实现被破坏时失败，而非仅验证 mock？
- 部署失败能否恢复，数据库变更是否兼容旧版本？
- 是否能够独立解释 AI 辅助生成的代码？

## 评审与模拟协作机制

个人学习也要留下真实评审闭环，不虚构团队经历：

1. 每个项目至少选一个高风险 diff，间隔半天后按清单做正式自审，记录范围、问题级别、证据、修复和回归测试。
2. 再让 AI 或同伴做一次独立审查；AI 意见只作候选，必须逐条验证。没有同伴时明确写“自审 + AI 复审”，不写成团队协作。
3. 评论分为**阻断、建议、疑问**，阻断项对应正确性、安全、数据或交付风险；没有发现问题也记录审查范围，不编造问题数量。
4. 项目 04 模拟一次需求变更：先澄清目标和验收，再评估影响、调整优先级并记录被延期的功能。
5. 有条件时参与一次真实同伴互评或开源贡献，保留链接和本人实际职责；没有条件不阻塞主线验收。

## 范围控制规则

- MVP 最多 3 条核心用户路径。
- 新想法默认进入“后续候选”，不在当前迭代顺手实现。
- 如果截止时间临近，优先减少非核心页面与扩展集成，不删除测试、安全和权限。
- 未完成项明确标记，不以截图、硬编码数据或关闭校验伪装完成。
