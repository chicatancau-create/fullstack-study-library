# 专项：鸿蒙 HarmonyOS ArkTS 与 ArkUI 应用开发

**定位：客户端/跨端岗位专项（P2）｜建议：8–10 周、80–120 小时｜前置：TypeScript、React 状态与组件、HTTP、Git、基础测试。**

> 可嵌入 D69–D84 的唯一岗位专项，或在 G9 后作为季度专项。主修鸿蒙时不同时主学 React Native/Flutter；复用 TS 与声明式 UI 思维，但生命周期、权限、构建、签名和真机行为必须重新学习。

## 一、先分清技术边界

- **ArkTS** 是 HarmonyOS 应用主力语言，保留 TypeScript 风格并强化静态检查；不能把任意 TS/JS 代码和 npm 包直接视为可运行。
- **ArkUI** 是声明式 UI 框架；组件、状态管理、布局和渲染机制与 React 相似但不等价。
- 当前原生应用以 **Stage 模型、UIAbility/ExtensionAbility** 为主；旧 FA 模型和旧全局路由示例只用于维护判断，不作为新项目默认方案。
- HarmonyOS 商业设备文档与 OpenHarmony 文档、不同 SDK/API 级别、不同设备能力不能混用。每个实验记录 DevEco Studio、SDK、目标设备/模拟器和文档日期。
- 不默认旧 Android 应用可直接运行，也不默认所有 Kit 在手机、平板、手表、车机上行为一致。

学习时使用官方受支持的稳定版本。不要把某个 API 号或 DevEco 版本写死为长期标准；升级前先读版本说明和 API 变更。

## 二、完成目标

完成后应能：

1. 从空工程实现一个可安装、可测试的 ArkTS/ArkUI 应用。
2. 解释组件状态、UIAbility 生命周期、Want、页面导航和后台切换的关系。
3. 完成本地持久化、网络请求、权限拒绝与恢复、进程重建后的状态恢复。
4. 处理手机常见尺寸、深色模式、字体缩放、键盘与基础无障碍。
5. 使用单元/UI/真机测试验证主流程和至少两类失败场景。
6. 用 Hvigor 完成可复现构建，理解证书、Profile、包签名和 AppGallery Connect 发布边界。
7. 说明哪些功能只在模拟器验证，哪些已由真实设备证明，不把预览器截图当作真机验收。

## 三、8 个教学单元

| 单元 | 核心内容 | 必须产出 |
| --- | --- | --- |
| 1. 环境与首个应用 | DevEco、SDK、Stage 工程、构建与日志 | 空工程在模拟器或设备启动，版本清单和首条构建记录 |
| 2. ArkTS 语言 | 静态类型、模块、空值、错误、集合并发边界 | 一个带运行时输入校验和单元测试的模型模块 |
| 3. ArkUI 与状态 | 声明式组件、状态归属、列表、表单、条件和异步更新 | 列表 → 详情 → 编辑主路径，处理空/错/加载 |
| 4. Stage 与导航 | UIAbility、生命周期、Want、Navigation、返回与恢复 | 后台切换、返回栈、进程重建和深链测试 |
| 5. 数据、网络与权限 | ArkData、文件、HTTP、取消、权限申请/拒绝/设置恢复 | 离线保存、失败重试、权限拒绝降级与数据迁移 |
| 6. 多设备与后台任务 | 响应式、资源、无障碍、受约束后台能力 | 常见尺寸/深色/字体验证，后台行为符合系统约束 |
| 7. 测试、性能与发布 | Hypium/UI 测试、启动/帧/内存、Hvigor、签名、AGC | 测试报告、性能基线、可复现签名包与发布说明 |
| 8. 综合作品 | 需求、架构、实现、失败、真机与交接 | 鸿蒙任务/内容应用及完整证据包 |

## 四、单元 1：环境与 Stage 工程

### 学习清单

- [ ] 安装当前稳定 DevEco Studio 与目标 SDK，记录安装路径、版本和环境变量。
- [ ] 创建 ArkTS + Stage 模型工程，理解 entry、module.json5、resources、pages 与 Ability 文件职责。
- [ ] 区分预览器、模拟器和真实设备；至少使用一种运行环境完成首次安装和日志查看。
- [ ] 首次构建保留命令、输出目录和错误原文，不以来源不明的脚本代替工程构建配置。

典型结构示意：

```text
entry/src/main/
├─ ets/
│  ├─ entryability/     # UIAbility 与生命周期
│  ├─ pages/            # 页面组件
│  ├─ components/       # 可复用组件
│  ├─ model/            # 数据模型与业务逻辑
│  └─ services/         # 网络、存储与系统能力边界
├─ resources/           # 字符串、颜色、图片与多设备资源
└─ module.json5         # 模块、Ability、权限等配置
```

### 最小 ArkUI 示例

```ts
@Entry
@Component
struct Index {
  @State count: number = 0

  build() {
    Column({ space: 16 }) {
      Text(`已完成 ${this.count} 项`)
        .fontSize(22)

      Button('新增一项')
        .onClick(() => {
          this.count += 1
        })
    }
    .padding(24)
  }
}
```

该例只用于理解声明式 UI 和状态驱动更新。状态装饰器、组件注册和构建规则以项目 SDK 的当前官方文档为准；不要为运行旧示例关闭类型检查。

## 五、单元 2–3：ArkTS、ArkUI 与状态管理

### ArkTS 重点

- [ ] 静态类型、可空值、接口/类型模型、泛型、模块和依赖边界。
- [ ] 外部 JSON/接口数据先运行时校验，不用 `any` 或断言掩盖协议变化。
- [ ] 错误分类、异步任务、取消和资源释放；UI 不直接承担全部业务逻辑。
- [ ] TaskPool、Worker、Sendable 的使用边界；并发不是简单复制 JS Promise 经验。

### ArkUI 重点

- [ ] 组件拆分、状态归属、单向数据流和列表更新。
- [ ] 表单校验、草稿、重复提交、加载/空/错误/无权限状态。
- [ ] 条件渲染、动画、手势和减少动态效果。
- [ ] 避免把父组件全部状态向下复制；重建时明确哪些状态可丢失、哪些必须恢复。

**练习：** 实现任务列表、筛选、详情和编辑，覆盖空列表、长文本、重复名称、保存失败、连续点击和返回未保存提醒。

## 六、单元 4：Stage 生命周期与导航

- [ ] AbilityStage、UIAbility、WindowStage 与页面/组件生命周期的职责区别。
- [ ] `onCreate/onForeground/onBackground/onDestroy` 等当前回调用于什么，不把页面重新显示误当成 Ability 重新创建。
- [ ] Want 的目标与参数、显式/隐式调用边界和输入校验。
- [ ] 使用当前 Navigation/NavDestination 与 UIContext 相关 API 管理页面栈；旧全局 router 示例先核对废弃状态。
- [ ] 返回、深层链接、横竖屏/窗口变化、后台回收和草稿恢复。

**必测：** 首页 → 详情 → 编辑 → 后台 → 返回；进程被回收后重新进入；深链带非法 ID；连续返回和重复打开同一页面。记录预期与实际，不凭界面“看起来还在”推断状态被保存。

## 七、单元 5：数据、网络、权限与后台行为

### 本地数据

- [ ] Preferences 适合简单偏好，关系型存储适合结构化查询，文件适合文档/导出；不要全部塞进一种存储。
- [ ] ArkData 的创建、迁移、并发写入、错误和备份边界。
- [ ] 敏感信息使用当前官方安全存储能力；令牌不写源码、日志或仓库。
- [ ] 数据库升级有版本和回滚策略，进程终止不产生半完成数据。

### 网络与系统能力

- [ ] HTTP 状态、解析、业务错误、超时、取消、重试和离线反馈分别处理。
- [ ] TLS/证书、Cleartext、Cookie/Token、服务端授权和敏感日志。
- [ ] 相机、位置、通知、相册等权限遵循最小化；申请前说明用途，拒绝后提供降级与设置恢复。
- [ ] 后台任务使用对应 Kit 的受约束模型，不以保活 hack 规避系统限制。

**练习：** 离线创建任务，联网后同步；注入超时、非 2xx、损坏 JSON、重复同步和权限拒绝，证明不会丢本地数据或重复创建服务端记录。

## 八、单元 6：多设备、体验与可访问性

- [ ] 使用资源与断点适配常见手机尺寸，横竖屏/折叠屏按真实目标设备选择验证。
- [ ] 深色模式、字体缩放、长文本、国际化占位和触摸目标。
- [ ] 语义、焦点、读屏标签、键盘/外设按设备支持情况验证。
- [ ] ArkWeb 只在确有 Web 内容需求时使用，核对安全、导航、脚本与原生桥接边界。
- [ ] 服务卡片、跨设备流转和分布式数据属于扩展；没有对应设备与账号条件时只做设计说明，不宣称验证通过。

## 九、单元 7：测试、性能、构建与发布

### 测试分层

- [ ] 单元测试覆盖模型、校验、状态机、存储迁移和同步幂等。
- [ ] UI 测试覆盖主路径、返回、权限拒绝、空/错状态和基本无障碍。
- [ ] 真实设备覆盖安装、生命周期、系统权限、后台切换、字体/深色和性能。
- [ ] 网络与系统能力替身不替代真机验证；每个 mock 写明未覆盖风险。

### 性能实验

选择启动、列表滚动、内存或后台任务中的一个：

1. 固定应用构建模式、设备、数据量和测量工具。
2. 记录基线、一次单变量改动和前后结果。
3. 检查预览器缓存/增量构建是否造成旧产物假象，必要时干净构建。
4. 不用截图大小、单个平均值或模拟器结果宣称真机性能。

### 构建、签名与发布

- [ ] 使用工程自带 Hvigor 配置完成 debug/release 构建，记录命令、产物和版本。
- [ ] 区分证书、私钥库、Profile、包名和设备 UDID；签名材料不进仓库或聊天。
- [ ] 核对签名包、版本号、包名与目标设备，不在签名后手工修改包内容。
- [ ] AppGallery Connect 的创建、测试分发、审核、隐私资料和发布按当期官方流程执行。
- [ ] 对外上传、真实账号操作、付费和正式发布需另行确认，不是课程默认动作。

## 十、综合作品：鸿蒙任务与内容管理应用

建议实现“离线任务清单 + 可选云端同步”，最多三条核心路径：

1. 任务列表/筛选 → 新建或编辑 → 本地保存；
2. 详情 → 状态变更 → 返回并保持状态；
3. 可选同步/导出 → 冲突、失败和恢复。

必须交付：

- [ ] 一页需求、非目标、数据模型、权限清单和页面/Ability 生命周期图。
- [ ] ArkTS 模型与 ArkUI 页面分层，外部数据有运行时校验。
- [ ] 本地持久化、迁移、空/错/加载和未保存草稿处理。
- [ ] 权限拒绝、网络失败、重复提交和进程重建测试。
- [ ] 单元/UI 测试、至少一个性能基线和一个真实 Bug 复盘。
- [ ] 可复现 Hvigor 构建、版本化签名说明和 README。
- [ ] 真机证据；没有设备时明确标注“仅模拟器/预览器验证”，不得写“真机通过”。
- [ ] 与 React 实现做一页对照：状态、导航、生命周期、生态、测试、打包和发布差异。

可选扩展：通知提醒、服务卡片、分享、跨设备协同、端侧 AI。扩展必须逐项验证设备、权限和系统版本，不为了堆能力破坏主路径。

## 十一、专项验收

- [ ] 能解释 ArkTS 与 TypeScript、ArkUI 与 React 的相同点和不可直接迁移部分。
- [ ] 能解释 UIAbility 与页面组件生命周期，并用日志证明一次后台/恢复行为。
- [ ] 离线、权限拒绝、进程重建和重复同步有明确行为与测试。
- [ ] 至少一项系统能力完成真实设备验证，或明确记录缺失设备导致的未验证边界。
- [ ] 构建可从干净环境复现，签名材料受控，发布版本与安装包一致。
- [ ] 作品包含失败、性能、安全和发布证据，而不是只有页面截图。
- [ ] 若选择鸿蒙作为岗位专项，将本作品与诊断/迁移证据登记到 G7 或季度专项。

## 十二、常见误区

- 把 ArkTS 当成“TypeScript 换皮”，直接复制 npm 项目而不检查 API 与运行时兼容性。
- 混用 HarmonyOS/OpenHarmony、FA/Stage、旧 router/新 Navigation 教程，却不核对版本。
- 只看预览器，忽略真实设备权限、后台回收、字体、签名和性能。
- 为追求“全场景”同时加入卡片、分布式、后台和 AI，主路径却没有测试。
- 把签名文件提交到仓库，或把构建出包直接等同于可上架。
- 没有目标设备仍宣称跨设备、分布式和真机兼容已验证。
