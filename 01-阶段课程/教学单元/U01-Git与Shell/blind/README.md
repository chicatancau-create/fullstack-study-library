# U01 盲测：独立未见任务

> 不附答案。要求在一台干净目录中独立完成，保留命令与原始输出；不得把 `examples/demo.sh` 原样复制后声称独立完成。

## 任务 A：冲突与历史

1. 在临时目录初始化仓库，默认分支为 `main`。
2. 创建 `base.txt`，内容三行：`one`、`two`、`three`，提交。
3. 创建 `left` 分支，把第二行改为 `two-left`，提交。
4. 回到 `main`，创建 `right` 分支，把第二行改为 `two-right`，提交。
5. 把 `right` 合并进 `left`，解决冲突，保留一行 `two-merged`，提交。
6. 把 `left` 合并进 `main`，解决冲突，提交。
7. 用 `git log --graph --oneline --all` 证明历史；用 `git grep -n '<<<<<<<'` 证明没有残留标记；用 `git status --porcelain` 证明工作区干净。

**交付**：命令序列、每步退出码、`git log --graph` 原始输出、冲突解决前后的文件内容。写清哪一步是 fast-forward、哪一步产生了 merge commit。

## 任务 B：Shell 管线与失败传播

给定一个日志文件 `access.log`（自己合成，至少 20 行，含空行、重复 IP、格式错误行）：

1. 统计非空行数。
2. 统计唯一 IP 数；格式错误行要计数并单独输出，不能静默丢弃。
3. 写一个脚本：默认 `set -euo pipefail`；当输入文件不存在时退出码非 0 且给出可读错误；当存在格式错误行时，默认不失败但打印数量，`--strict` 时失败。
4. 故意让上游命令失败（例如 `cat missing | wc -l`），证明默认管道会掩盖失败、`pipefail` 会暴露失败。

**交付**：脚本、合成日志、正常/缺失/`--strict` 三种运行的命令与退出码。不得用 `|| true` 吞掉失败来“通过”。

## 评分要点（自评，不是外部验收）

- 冲突是否真正解决，而不是删掉一整边内容蒙混。
- 是否解释了 merge commit 与 fast-forward 的区别。
- 失败是否以非零退出码传播，而不是只打印。
- 输出是否可被他人按 README 复现。
