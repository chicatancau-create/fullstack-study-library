# 专项：uni-app 与 uni-app x 跨端应用开发

**定位：Vue 跨端岗位专项（P2）｜建议：6–8 周、70–110 小时｜前置：TypeScript、Vue 3、HTTP、Git、基础测试。**

> uni-app 是跨端应用框架，不是独立编程语言。学习重点不是再记一套“语法”，而是理解同一份 Vue/TS/CSS 代码如何经编译器进入 Web、小程序、App 与鸿蒙等不同运行时，以及各端在生命周期、渲染、权限、存储、签名和发布上的真实差异。

## 一、先分清技术边界

- **uni-app** 使用 Vue 单文件组件、组件标签和 `uni.*` API，通过编译器生成各端运行物；Web、小程序、App 的运行时并不相同。
- **uni-app x** 是 uni-app 的新一代跨端方案，App 端采用原生渲染，使用 `.uvue`、CSS 子集和 UTS 原生扩展能力；不能把 uni-app 示例直接当作 uni-app x 示例。
- uni-app x 的早期 VDOM 模式与 2026 年后的蒸汽模式在语言、渲染引擎和升级路径上不同。选择项目模式前先读当期官方文档，不把某个 HBuilderX 版本写死为长期标准。
- 条件编译解决的是“同一工程里的平台差异”，不是把业务逻辑复制成多套。大量平台专属代码仍应下沉到服务、适配器或原生插件边界。
- 非 Web 端通常区分逻辑层与渲染层。逻辑层不能随意使用浏览器专用 `window`、DOM API；需要操作渲染层时使用官方规定的机制。

## 二、完成目标

完成后应能：

1. 说明 uni-app 与 uni-app x 的编译目标、渲染方式、适用场景和迁移成本。
2. 从空工程实现一个可运行、可测试、可发布的跨端任务应用。
3. 正确区分应用生命周期、页面生命周期与 Vue 组件生命周期，并解释触发顺序。
4. 使用条件编译处理 API、组件、样式和 `pages.json` 的平台差异。
5. 完成本地存储、网络请求、权限拒绝、离线恢复和重复提交等失败路径。
6. 为至少两个真实目标端准备构建、签名或发布配置，并说明哪些结果只在模拟器或开发者工具中验证。
7. 用自动化测试、真机检查和性能实验证明主流程，不以单端截图宣称“全端通过”。

## 四、单元 1–2：选型与工程结构

### 选型清单

- [ ] 明确目标用户优先使用 Web、小程序、Android/iOS App、鸿蒙中的哪些端。
- [ ] 对比 uni-app 与 uni-app x 的渲染方式、CSS 能力、原生插件、包体、热更新和迁移成本。
- [ ] 记录 HBuilderX/CLI、Vue、uni-app 编译器、目标 SDK、设备系统和文档访问日期。
- [ ] 已有 uni-app 项目升级 uni-app x 时，先做组件、CSS、插件与原生 API 清单，不直接整仓替换。

典型工程职责：

```text
project/
├─ App.vue 或 App.uvue   # 应用入口、应用生命周期、全局样式与 globalData
├─ main.ts               # Vue 应用、插件与全局依赖装配
├─ pages/                # 页面级 SFC
├─ components/           # 可复用组件
├─ services/             # HTTP、存储与平台能力适配
├─ static/               # 不参与编译的静态资源
├─ pages.json            # 页面、导航栏、tabBar、分包与条件编译
└─ manifest.json         # Appid、各端打包、权限与 SDK 配置
```

`pages.json` 与 `manifest.json` 可包含注释和平台专属节点，不能按严格 JSON 解析器的结果直接判定文件损坏。修改前先确认所用编译器支持对应字段。

## 五、单元 3：Vue 3、组件与状态

- [ ] 页面使用 Vue SFC，组件状态归属清晰；不把全部业务状态塞进 `globalData`。
- [ ] 列表、筛选、详情、编辑共享同一数据契约，表单有校验、草稿、重复提交和失败恢复。
- [ ] 外部响应先做运行时校验，不用 `any` 或类型断言掩盖接口变化。
- [ ] 页面销毁时取消监听、定时器和未完成请求，避免过期响应覆盖新状态。
- [ ] 跨端组件命名接近小程序规范，但可移植性仍受渲染引擎、CSS 子集和插件支持限制。

**练习：** 实现“任务列表 → 新建/编辑 → 本地保存 → 返回列表”，覆盖空列表、长文本、非法 ID、保存失败、连续点击和返回未保存提醒。

## 六、单元 4：三层生命周期

### 应用生命周期

`onLaunch`、`onShow`、`onHide`、`onError` 等应用级回调只在应用入口文件中有效。`onLaunch` 全局只触发一次；应用从后台回前台会再次触发应用 `onShow`，不能把它当成页面重新创建。

### 页面生命周期

常用页面回调包括：

- `onLoad`：接收页面参数，适合尽早发起异步取数，不适合执行大量同步计算或直接操作尚不存在的页面 DOM。
- `onShow`：页面每次显示时触发，包括从下级页面返回。
- `onReady`：页面初次渲染完成，可访问渲染后的节点信息。
- `onHide`：页面被其他页面覆盖或切走。
- `onUnload`：页面卸载，应释放监听和临时资源。
- `onPullDownRefresh`、`onReachBottom`、`onBackPress`：按平台和页面能力使用，不能假设所有端行为一致。

### 组件生命周期

组件仍遵循 Vue 标准生命周期。页面级 `onLoad` 不会自动出现在子组件中；子组件应通过 props、事件、依赖注入或 store 与页面协作，而不是依赖隐式页面栈顺序。

**必测路径：** 冷启动 → 首页 → 详情 → 编辑 → 返回 → 后台 → 前台 → 再次返回。记录应用、页面、组件三层回调的实际顺序，并区分“页面隐藏”“页面卸载”“应用退后台”。

## 七、单元 5：条件编译与平台差异

条件编译使用 `#ifdef`、`#ifndef` 与 `#endif`，可作用于脚本、模板、样式、`pages.json`、部分目录和预编译语言。常见平台标识包括 `APP-PLUS`、`APP-HARMONY`、`WEB`/`H5`、`MP-WEIXIN`、`MP` 等；具体可用值以当期编译器文档为准。

```vue
<script setup>
// #ifdef APP-PLUS
console.log('仅 App 平台编译')
// #endif

// #ifndef MP-WEIXIN
console.log('除微信小程序以外的平台')
// #endif
</script>
```

规则：

1. 条件块内与条件块外都必须保持语法正确；JSON 不能因条件编译留下尾随逗号或重复键。
2. 先封装共享能力，只有真实平台差异才条件编译，避免把同一业务复制成多份。
3. API、组件、CSS 和配置差异分别建立矩阵，每格写明“已验证/仅文档支持/不适用”。
4. 低版本编译器不认识平台标识时，`#ifdef` 与 `#ifndef` 的结果可能不对称；升级前核对版本说明。
5. 原生能力优先使用官方跨端 API；端专属能力放在明确适配层，不散落进页面组件。

## 八、单元 6：数据、网络、权限与原生能力

### 本地数据

- [ ] 小型偏好、结构化数据、文件和缓存分开选择，不把全部状态塞进一种存储。
- [ ] 写入有版本、失败处理与恢复策略；进程退出不能留下半完成数据。
- [ ] 令牌、私钥、签名材料和用户隐私不写源码、日志或学习仓库。
- [ ] 离线创建的数据在重新联网时有幂等同步、冲突提示和重复提交保护。

### 网络与系统能力

- [ ] HTTP 状态、业务错误、超时、取消、重试和离线反馈分别处理。
- [ ] TLS、Cookie/Token、服务端授权和敏感日志按目标端能力核对。
- [ ] 相机、位置、相册、通知等权限遵循最小化；拒绝后提供降级路径和设置入口。
- [ ] 推送、分享、支付、升级等插件逐项检查平台、版本、包名、证书与隐私政策。
- [ ] uni-app x 的原生扩展可能涉及 UTS、原生插件和端专属生命周期，不能沿用普通 Web 假设。

**练习：** 注入超时、非 2xx、损坏 JSON、重复同步、权限拒绝和应用后台回收，证明本地数据不丢、服务端记录不重复、用户能恢复操作。

## 九、单元 7：测试、性能与诊断

### 测试分层

- [ ] 单元测试覆盖模型、校验、状态转换、存储迁移和同步幂等。
- [ ] 页面自动化测试覆盖跳转、点击、元素状态、文本与截图；平台支持范围以当期 uni-app(x) 自动化测试文档为准。
- [ ] Web 可用浏览器工具，小程序使用对应开发者工具，App 至少完成真实设备或明确标注的模拟器验证。
- [ ] mock 只能证明已覆盖的分支，每个替身都要写明未验证的原生权限、网络和系统行为。

### 性能实验

选择启动、长列表或页面切换中的一项：

1. 固定设备、构建模式、数据量和测量工具。
2. 记录基线，只做一个变量改动，再记录结果。
3. 检查增量构建、缓存和旧产物是否造成假象，必要时干净构建。
4. 分别报告首屏、可交互、滚动帧率与内存，不用单张截图或平均值代替完整结论。

## 十、单元 8：构建、签名与发布

- [ ] 记录每个端的构建命令、产物路径、版本号、包名/Appid 和依赖版本。
- [ ] App 发布区分 debug/release、证书、私钥、Profile、包名和升级策略；签名材料不进仓库。
- [ ] 小程序发布检查 Appid、域名白名单、隐私接口、类目、审核版本与体验版二维码。
- [ ] Web 发布检查路由模式、静态资源、HTTPS、缓存策略和回滚产物。
- [ ] 鸿蒙目标按当期官方工程、证书与应用市场流程处理，不把 Android 打包步骤照搬为鸿蒙流程。
- [ ] 对外上传、真实账号操作、付费服务和正式发布需另行确认，不是课程默认动作。

## 十一、综合作品：跨端任务管理应用

建议实现“离线任务清单 + 可选云端同步”，最多三条核心路径：

1. 任务列表/筛选 → 新建或编辑 → 本地保存；
2. 详情 → 状态变更 → 返回并保持状态；
3. 可选同步/导出 → 冲突、失败和恢复。

必须交付：

- [ ] 一页需求、非目标、数据模型、权限清单、目标端矩阵和生命周期图。
- [ ] Vue 页面、组件、服务与平台适配层分离，外部数据有运行时校验。
- [ ] 本地持久化、空/错/加载、未保存草稿和进程恢复处理。
- [ ] 至少三端条件编译差异与对应测试证据。
- [ ] 一个真实 Bug 的复现、根因、修复和回归记录。
- [ ] 可复现构建、版本化发布说明和未验证项清单。
- [ ] 与 [[专项-鸿蒙ArkTS与ArkUI应用开发|鸿蒙专项]] 做一页对照：生命周期、状态、导航、权限、测试、打包和发布差异。

可选扩展：通知、分享、深色模式、国际化、离线包或端侧能力。扩展必须逐项验证目标端，不为了展示“全端能力”破坏主路径。

## 十二、专项验收

- [ ] 能解释 uni-app 与 uni-app x 的编译、渲染和生态边界，并给出选型理由。
- [ ] 能用日志证明应用、页面、组件生命周期在冷启动、返回和后台切换中的实际顺序。
- [ ] 条件编译后的代码在目标平台语法正确，且差异矩阵有测试或明确未验证标记。
- [ ] 离线、权限拒绝、网络失败、重复提交和进程恢复有明确行为。
- [ ] 至少两个目标端完成真实构建；只有一个端实测时不得写“全端通过”。
- [ ] 作品包含失败、性能、安全和发布证据，而不是只有页面截图。
- [ ] 若选择 uni-app 作为岗位专项，将作品与诊断证据登记到 G7 或季度专项。

## 十三、常见误区

- 把 uni-app 当成“一门语言”，或把 Vue 语法等价于所有端运行时能力一致。
- 混用 uni-app、uni-app x、nvue、uvue 示例，不核对编译器与目标端。
- 在逻辑层调用浏览器 DOM，或在非 Web 端假设 `window` 永远存在。
- 用条件编译复制整套业务，导致公共逻辑无法维护。
- 只看 H5 或模拟器，忽略真机权限、后台回收、签名、隐私审核和商店分发。
- 把插件市场中的示例直接当生产依赖，不检查许可、维护状态、平台版本和原生 API。
- 把“能打包”等同于“能发布”，把“已提交审核”等同于“已通过验收”。
