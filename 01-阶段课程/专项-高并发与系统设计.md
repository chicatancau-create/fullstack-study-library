# 专项：高并发与系统设计

> 排期口径：本页原第 1–52 周属于 C 压缩主题索引；深度路线实际日期与关口以 [[../03-执行计划/深度路线与工时预算|D01–D96 / G0–G9]] 为准。核心实验可复用项目证据，算法与实验工时已计入总预算。

**定位：从“能交付应用”升级为“能分析规模、瓶颈、失败与成本”｜优先级：P1｜建议从第 21 周开始，每四周一个设计。**

> 系统设计不以组件数量评分。每个答案必须能回到业务约束、数据流、容量、失败和验证；至少一个主题要实现成可运行原型，不能只画架构图。

## 一、统一设计流程

每次限时 45–60 分钟，按以下顺序输出：

1. **澄清范围**：用户、核心路径、非目标、读写比例和一致性要求。
2. **容量估算**：DAU、峰值 QPS、数据增长、存储、带宽、连接数和成本数量级；假设必须写明。
3. **契约与模型**：核心 API、数据模型、状态机、权限和业务不变量。
4. **主链路设计**：读/写路径、同步/异步边界、缓存、数据库、队列和外部依赖。
5. **瓶颈与单点**：热点、锁、连接池、序列化、网络、磁盘、慢查询、排队和故障域。
6. **可靠性**：超时、重试、幂等、限流、熔断、降级、隔离、恢复和人工处置。
7. **安全与成本**：认证授权、滥用、数据最小化、供应链、资源和云服务成本。
8. **验证与演进**：SLO、负载/故障实验、监控告警、Runbook、下一阶段扩展与回滚。

不允许先画微服务再补需求，也不允许用“加缓存、加 Kafka、上 K8s”代替具体分析。

## 二、十二类核心设计题

| 主题 | 核心追问 | 最低实验或证据 |
| --- | --- | --- |
| 限流器 | 固定/滑动窗口、令牌桶、分布式一致性、突发流量 | 单机原型 + Redis/共享状态对比与竞态测试 |
| 短链接 | 唯一 ID、映射、重定向、缓存、滥用和统计 | 写路径、读路径、冲突和过期策略 |
| 分布式 KV | 分区、复制、一致性哈希、热点和故障恢复 | 数据迁移、节点失效和一致性说明 |
| 唯一 ID 生成 | 自增、UUID、Snowflake、时钟回拨和热点 | 并发唯一性、时钟异常与性能实验 |
| 消息/通知系统 | 至少一次、顺序、重试、死信、积压和幂等 | 重复消息、Broker 故障和恢复测试 |
| Feed 流 | 读/写扩散、大 V、分页、排序、缓存和去重 | 数据模型、时间线原型与热点分析 |
| IM/实时通信 | 在线状态、消息顺序、 ack、重连和离线同步 | 断线、重复、乱序和权限测试 |
| 秒杀/抢购 | 热点库存、削峰、排队、超卖和降级 | 并发库存、限流与压测报告 |
| 搜索自动补全 | Trie/索引、更新、分片、相关性和延迟 | 前缀索引原型与大数据量策略 |
| 支付/交易一致性 | 状态机、幂等、对账、补偿和审计 | 重复回调、半失败和恢复实验；不接真实资金 |
| 对象存储与 CDN | 分片、元数据、签名 URL、缓存和生命周期 | 上传权限、恶意文件、失效和成本分析 |
| RAG/Agent 平台 | 检索质量、工具权限、状态、评测、成本和注入 | 评估集、追踪、无答案与故障策略 |

## 三、毕业项目的深度扩展

保留现有 [[../02-项目实战/项目04-综合SaaS毕业项目|综合 SaaS]] 业务交付要求，同时从下面选择一个深度模块，不强制更换题目：

### A. 高并发交易/预约模块

- 热点资源竞争、幂等、排队或原子扣减。
- 限流、缓存、异步任务、状态机和审计。
- 明确一致性边界，不默认使用分布式锁解决所有问题。

### B. Feed/内容分发模块

- 关注关系、时间线、读/写扩散选择和稳定分页。
- 热点作者、缓存失效、去重和降级。
- 以数据量和读写比证明模型选择。

### C. 实时通知/调度模块

- Outbox、优先级、公平调度、重试、死信和幂等消费。
- 断线、重复、乱序、积压和恢复。
- 队列深度、处理速率、 oldest-age 等可行动指标。

### D. RAG/Agent 模块

- 文档解析、混合检索、重排、引用和无答案策略。
- 工具权限、人工审批、状态与轨迹。
- 评估集、Token 成本、P95 时延、提示注入和敏感数据验证。

## 四、负载、可靠性与成本验收

### 负载实验

- 记录硬件/容器限制、运行时版本、数据量、索引、缓存和工具参数。
- 先基线后单变量优化，报告吞吐、P50/P95/P99、错误率和饱和度。
- 至少包含普通负载、峰值/热点和超过容量三种场景。
- 不用本机一次请求或平均值宣称高并发能力。

### 故障实验

至少注入两类：数据库慢/不可用、缓存失效、消息重复/积压、下游超时、Pod 退出、时钟异常或网络延迟。

每次记录：

- 注入方法与影响范围；
- 发现指标和告警；
- 系统是否符合预期降级；
- 数据是否保持权限与不变量；
- 恢复步骤、耗时和遗留风险；
- 需要增加的回归测试。

### 成本与演进

- 估算主要计算、存储、带宽、消息与第三方调用成本。
- 说明当前规模下哪些组件不应引入，以及触发扩容/拆分的可观察条件。
- 区分真实测量、容量假设和面试推演，不虚构生产用户量。

## 五、交付物模板

每个设计或模块至少归档：

1. 一页需求与容量假设；
2. 架构图、ER/数据模型、状态机或时序图；
3. API 与权限矩阵；
4. 关键 ADR：候选、取舍、代价和退出条件；
5. 压测/故障实验脚本与原始结果；
6. 监控面板、告警和 Runbook；
7. 已知限制、未验证范围和下一轮优先级；
8. 20 分钟技术讲解与一次限时模拟设计记录。

## 六、阶段验收

- [ ] 能先澄清需求和容量，再讨论组件与架构。
- [ ] 至少一个主题有可运行原型，不是只有架构图。
- [ ] 至少一次性能优化有同口径前后对照。
- [ ] 至少两类故障有注入、恢复和回归证据。
- [ ] 能解释热点、一致性、幂等、重试、降级和数据权限。
- [ ] 能说明当前简单方案为何足够，以及何时需要演进。
- [ ] 所有规模、性能和 AI 指标均标明来源与未验证边界。

## 七、常见误区

- 用微服务、Kafka、Redis、Kubernetes 的数量衡量架构水平。
- 不做容量估算，直接宣称支持百万/亿级流量。
- 只看吞吐量，不看尾延迟、错误率、排队、资源和成本。
- 把重试当可靠性，忽略幂等、重试预算和故障放大。
- 把 AI 应用包装成普通 CRUD，没有评估集、权限、成本和失败边界。
- 用模拟数据得出的结果冒充真实生产经验。
