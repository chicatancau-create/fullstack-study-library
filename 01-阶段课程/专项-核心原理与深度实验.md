## 一、共同实验协议

每个实验记录：问题与假设 → 所依据的官方版本文档 → 最小装置/输入 → 正常与失败对照 → 原始结果 → 根因与修复 → 相同条件回归 → 适用边界。使用 [[../03-执行计划/模板-能力证据|能力证据模板]]，关联代码提交与命令。

至少包含一个可证伪假设；观察结果与假设不一致时保留结果并修正解释。不能预先写成功结论，也不能把“没有崩溃”当作资源安全证明。正常/异常/并发结果必须可重复，测量不足时说明限制。

## 二、实验清单

### E01：C 内存、资源与编译（G1，后续 G5 加深）

- 前置：基础语法、编译器与调试器；先实现动态数组，再做哈希表。
- 机制：值/指针、所有权、栈/堆、布局与生命周期；预处理、编译、链接、符号。
- 动作：测试容量 0/1、扩容、重复键和分配失败的可控替身；注入一次越界或释放后使用，用 Sanitizer/调试器定位。
- 深挖：观察对象布局与对齐；读写文件处理短读/短写、错误和关闭。文件 KV/内存池是系统方向扩展，不是 G1 入门门槛。
- 验收：失败证据指向具体位置；修复后的同一测试通过；释放与边界检查有证据，明确工具覆盖不到什么。

### E02：异步执行、取消与背压（G2/G4）

- 机制：JS 调用栈、任务/微任务；Node 事件循环与工作线程池；Promise 不等于自动并行。
- 动作：实现有并发上限、超时和取消的任务池；测试乱序完成、首项失败、取消时已有任务/待运行任务的处理，以及所有 Promise 的结算。
- 反例：无限并发、同步 CPU 忙循环、忽略流消费速度；观察事件循环延迟、内存/待处理任务增长。
- 验收：无无界队列/无限重试；超时不被误认为底层操作已撤销；停止接收与资源清理语义清楚。改变生产/消费速率后仍有界。

### E03：React 状态、渲染与前端竞态（G3）

- 机制：render/commit、状态快照、key、Effect 依赖与清理，开发模式额外检查与生产行为区别。
- 动作：快速切换 A/B 筛选，让 A 迟于 B 返回；先复现旧结果覆盖，再用取消/版本校验修复。测试乐观更新失败回滚和路由卸载。
- 深挖：比较派生状态、事件处理与 Effect；Profiler 定位一次真实渲染/长任务问题，再验证用户可观察行为。
- 验收：确定性控制响应顺序的测试；修复后旧结果不能覆盖新状态；不用减少渲染次数作为唯一优化指标。

### E04：HTTP、缓存、Cookie 与网络失败（G1/G5）

- 机制：DNS/TCP/TLS/HTTP，连接复用、缓存新鲜度与验证；同源/CORS 与凭据边界。
- 动作：抓一次受控 HTTPS 请求的网络时序；记录 Cache-Control、ETag/304、Vary；分别注入 DNS 错误、连接拒绝、慢响应和 HTTP 5xx，区分发生层次。
- 反例：个性化响应被共享缓存；预检成功却缺认证；客户端超时后服务端已提交。
- 验收：不要求解密未知流量；能从可见证据区分请求未发出、服务端拒绝、响应丢失与结果未知，并为未知结果设计幂等查询/恢复。

### E05：构建、渲染模式与可访问性（G3/G6）

- 机制：ESM、Tree Shaking、副作用、动态导入、source map；CSR/SSR/SSG、hydration、服务端/客户端边界。
- 动作：分析一次生产产物、路由懒加载与缓存更新；同一内容页做 CSR 与 SSG/SSR 最小对照，检查首屏、SEO、缓存和运维代价。
- 反例：旧 HTML 引用已删除的 chunk、hydration 不一致、服务端缓存串用户、客户端环境变量泄漏。
- 可访问性：键盘与焦点、读屏抽测、400% 缩放/等效 320 CSS px 重排（适用例外说明）、减少动态效果；自动工具之外记录人工结论。
- 验收：渲染模式选择有约束与测量，秘密不进入前端产物；UI 不是只在理想网络和鼠标下可用。主线先掌握 React，元框架深入后置到岗位专项。

### E06：操作系统与运行时诊断（G5/G7）

- 机制：进程/线程/协程、调度、虚拟内存、文件描述符、阻塞/非阻塞 I/O、连接池与资源限制。
- 动作：在受控程序注入 CPU 忙循环、内存/句柄增长、连接池耗尽三类问题，至少独立诊断其中两类。
- 主修：Node 用 CPU/Heap Profile 与事件循环指标；Java 用 JFR/线程转储/GC；Go 用 pprof/trace/race；Python 用 profiler/asyncio 任务与相应构建模式说明。
- 验收：把系统指标与调用栈/分配证据连接到根因；同口径回归；不是重启后无错就宣称修好。并发理论必须注明语言内存模型与运行时版本。

### E07：事务隔离、Owner 与库存不变量（G4/G5）

- 前置：真实 PostgreSQL、连接/事务、唯一/外键/检查约束。
- 动作：用两个独立连接和显式同步屏障复现“两个 Owner 各自删除对方”写偏差；记录所用隔离级别、语句顺序与最终状态。
- 修复候选：锁定同一工作区父行并统一锁顺序；Serializable 加受控重试；其他方案须证明覆盖所有写路径。只锁各自成员行或各自做 count 不足以自动保证规则。
- 库存实验：条件更新/行锁与事务、并发扣减、取消和回调竞争；验证扣减与状态转换原子性。
- 验收：全路径无法移除最后 Owner；库存非负，失败没有半状态；死锁/序列化失败有有界重试和幂等保护。说明测试不是形式化并发正确性证明。

### E08：执行计划、数据分布与迁移恢复（G4/G6）

- 动作：构造可重复的合成数据，包含倾斜分布/NULL/热点；对一个过滤+排序/关联查询读执行计划，再比较一个索引或 SQL 调整。
- 机制：选择性、复合索引顺序、扫描/连接、统计信息、读写成本；PG/MySQL 的 MVCC/锁/执行器细节分别查证。
- 迁移：旧版本→新增可兼容字段→回填→双读/切换（按需要）→验证→收缩，记录旧新应用兼容矩阵。
- 恢复：备份还原到独立库，核对行数、关键校验/约束、业务可读性与实际 RPO/RTO；恢复后考虑已删除数据不应被重新上线暴露。
- 验收：同数据/环境对照；数据操作前有快照。解释代码回滚与数据恢复的区别，不能对有新写入的库盲目覆盖恢复。

### E09：缓存并发与过期写回（G5）

- 动作：显式调度旧读/写库/删缓存/旧结果回填交错，复现 Cache Aside 仍出现短暂旧值；停止 Redis，注入热点 miss。
- 机制：缓存不是事实源；TTL 只界定部分过期窗口，不能自动保证强一致；击穿保护与负缓存的业务边界。
- 验收：声明允许陈旧窗口、失效/版本策略、过载保护及恢复；对强一致路径绕开缓存或选择经验证的协议。缓存故障不改变权限与库存正确性。

### E10：Outbox、幂等与消息崩溃窗口（G5/G7）

- 动作：业务行与 Outbox 同事务提交；Worker 在“发送前”“发送后未标记”“消费提交后未 ack”处可控停止并重启。
- 消费者：事件 ID 去重与业务副作用在同库事务内；外部副作用另用幂等接口或对账，不宣称被本地事务自动覆盖。
- 幂等请求：key + 用户/租户 + 请求指纹；同 key 不同内容返回冲突；验证并发、处理中、已完成、失败重试和过期边界。
- 深挖：顺序、重复、退避/抖动、死信、重放与积压；消息保留/幂等记录清理必须匹配重放窗口。
- 验收：重复投递不会重复可控副作用，已提交事件最终可恢复处理；有对账与失败人工处置；明确“至少一次”及实际保证范围。G5 可先用任务表，G7 用一种真实 Broker 验证。

### E11：跨边界授权与安全失败（G4–G6）

- 按数据流画信任边界，使用合成的两个租户、至少两类角色。
- 除列表/详情/修改外，还测搜索、聚合计数、缓存 key、文件 URL、导出、后台任务、消息和日志中的隔离。
- 测试会话过期/注销、权限撤销后的行为；上传类型/路径/大小、SQL 参数化、XSS 输出上下文、CSRF（按方案）、SSRF/开放重定向（适用时）。
- 逐项映射 OWASP Top 10:2025，并参考 ASVS 相应要求定义可测控制；风险榜单不是完整测试规范，未适用项写理由。
- 验收：失败时不泄露堆栈、秘密或他人数据；有测试和清理记录；只扫描或隐藏前端按钮均不算授权验收。

### E12：负载模型、排队与容量（G5/G7）

- 定义工作负载、请求组合、数据分布、成功业务结果、目标/阈值与环境；在测试前固定判定条件。
- 比较稳态、突发/热点、超容量；说明开放到达率与封闭并发模型，警惕 coordinated omission 和压测端自身饱和。
- 固定随机种子、数据集与缓存状态；预热后至少三轮同口径测量，保留原始样本/汇总并说明波动。
- 报告完成的业务吞吐、P50/P95/P99、错误率、超时、排队、CPU/内存/池饱和度；小样本不强行解释 P99。
- 用 Little 定律核对平均在途量≈到达率×平均停留时间及其稳定系统前提；不是套公式预测所有负载。
- 验收：先定位一个瓶颈再单变量优化，回测正确性与尾延迟；标明本地容量不能外推为真实大厂流量。

### E13：SLO、兼容发布与恢复（G5/G6）

- 选一条业务路径定义 SLI 的好事件/有效总事件与窗口；为实验设 SLO 与错误预算，明确是训练目标。
- 用固定窗口计算预算，例如 30 天时间可用性 99.9% 对应 43.2 分钟，仅适用于时间口径；请求成功率预算应按请求数计算，不能混用。
- 发布不可变制品，先验证旧/新代码与旧/新 schema 的兼容；练一次服务回滚和一次独立库恢复。
- 注入至少两类故障：DB 慢/不可用、缓存停机、消息重复/积压、Pod 退出、下游超时等；只作用于隔离资源。
- 验收：指标发现影响→告警→Runbook→恢复→数据核对→复盘；记录实际恢复耗时与 RPO/RTO。错误预算告警不只看 CPU 高低。

## 三、深挖问答：每项都要能回答

1. 现象可能由哪三类根因造成？下一步最便宜的区分实验是什么？
2. 哪个反例会推翻当前方案？测试是否真的覆盖了这个交错或输入？
3. 数据量扩大十倍、网络变慢、权限撤销或进程中止后，保证还成立吗？
4. 哪些结论来自规范，哪些来自当前实现/版本，哪些只是推断？
5. 如果去掉一个组件，哪些正确性/性能/维护能力会变化？
6. 方案如何回滚、重放、对账，谁接到告警后能操作？

## 四、完成标准

E01–E13 每个实验包都有复现输入、失败证据、实际结果和边界说明；无需重复保存同一证据，但每条验收要能准确引用。只在自己机器自测时如实标记，外部复核尚未完成时不能写已交接通过。

项目中发现真实问题时按项目复盘记录；本文件是实验设计，不表示这些问题已在学习者项目中发生或被修复。生产故障注入、真实数据恢复和外部服务操作必须另行获得授权。
